# 프롤로그 — 왜 앤스로픽의 시니어 엔지니어들은 코드를 먼저 치지 않는가?

::: {.ch-sub}
명세와 데이터 구조가 곧 시스템의 헌법이다
:::


<!-- 여기부터 본문 -->


터미널을 열고 프롬프트를 입력합니다. 번뜩이는 아이디어를 몇 줄의 자연어로 던지자, 거대언어모델(LLM)이 불과 수초 만에 수백 줄의 코드를 토해냅니다. 동작하는 버튼, 유려한 스타일의 웹 페이지, 그럴듯한 데이터베이스 호출 로직까지 눈앞에 펼쳐집니다. 처음 이 마법을 경험했을 때 우리는 누구나 같은 착각에 빠집니다. "이제 개발은 끝났다. 프롬프트 몇 줄이면 누구나 하루 만에 유니콘 서비스를 만들 수 있겠구나."

그러나 비즈니스 로직이 한 단계 깊어지는 순간, 현실은 가혹하게 본색을 드러냅니다.

기존 데이터베이스에 외래 키(Foreign Key) 하나를 추가하고 복합 인덱스를 적용해 달라고 요청하는 순간, AI는 이전 대화에서 작성했던 핵심 비즈니스 로직을 멋대로 지워버립니다. 결제 웹훅 처리 코드를 요청했더니 프론트엔드 상태 관리 라이브러리를 통째로 갈아치웁니다. 에러 로그를 붙여 넣으며 "수정해 줘"를 연발할수록 코드는 기하급수적으로 꼬여가고, 결국 수천 줄의 스파게티 코드 속에서 길을 잃은 엔지니어는 깊은 한숨과 함께 `git reset --hard`를 입력합니다.

소프트웨어 개발의 역사에서 생산성을 높이기 위해 등장했던 수많은 도구 중, 이토록 빠르고 매혹적이면서 동시에 이토록 치명적인 기술 부채를 순식간에 양산해낸 도구는 없었습니다.

## '프롬프트 만능주의'라는 위험한 신기루

우리는 왜 이 거대한 벽에 부딪히는 것일까요? 모델의 지능이 부족해서일까요? 파라미터 수가 모자라서일까요?

그렇지 않습니다. 근본적인 원인은 모델의 성능이 아니라 **인간 엔지니어가 AI에게 일을 시키는 방식의 부재**에 있습니다.

현재 업계에 만연한 이른바 '바이브 코딩(Vibe Coding)' 혹은 '프롬프트 엔지니어링 팁'이라 불리는 방식은 실리콘밸리의 미시적 실험실에서는 통할지 몰라도, 엔터프라이즈 환경이나 상용 SaaS 프로덕션 레벨에서는 통하지 않습니다. 머릿속에 떠오른 생각을 정제되지 않은 자연어로 두서없이 던지는 행위는, 신입 주니어 개발자에게 구두로 대충 설명하고 곧바로 프로덕션 배포 코드를 짜오라고 등을 떠미는 것과 다를 바 없습니다.

AI는 문맥이 모호할수록 확률적 빈칸 채우기(Next-token Prediction)에 의존합니다. 기획의 경계선이 어디까지인지, 데이터 스키마의 무결성 제약 조건이 무엇인지, 이번 스프린트에서 절대 건드려서는 안 되는 레거시 영역이 어디인지 선언하지 않은 채 던지는 프롬프트는 필연적으로 [컨텍스트 오염(Context Drift)]{.dot}과 시스템 붕괴를 초래합니다.

## 앤스로픽이 코드를 치지 않는 이유

세계에서 가장 정교한 프론티어 AI를 만들고, 에이전트 CLI와 프로토콜을 주도하는 앤스로픽(Anthropic)의 본사 엔지니어들은 이 문제를 어떻게 해결하고 있을까요?

그들은 키보드를 잡자마자 프롬프트를 난사하거나 코드를 작성하지 않습니다. 대신 **명세(Specification)를 먼저 선언하고 합의합니다.**

앤스로픽의 엔지니어링 철학을 관통하는 가장 중요한 개념은 **헌법적 가드레일(Constitutional Guardrail)** 입니다. 시스템의 동작 원칙, 보안 규칙, 데이터의 타입과 제약 조건, 아키텍처의 경계선을 사람이 먼저 명확한 텍스트로 정의합니다. 이것이 바로 마크다운 형태로 리포지토리에 저장되는 **단일 진실 공급원(Single Source of Truth, SSOT)** 입니다.

명세가 확정되지 않은 상태에서 작성된 코드는 쓰레기(Garbage)에 불과합니다. 반대로 다음 네 단계의 명세가 수학적 수준으로 정밀하게 선언되어 있다면, AI는 더 이상 통제 불능의 생성기가 아니라 세상에서 가장 빠르고 정확한 [지능형 컴파일러]{.dot}로 탈바꿈합니다.

::: {.formula}
[4대 명세 체계]{.label}

기획(PRD) → 시스템 아키텍처(Architecture) → 데이터 스키마(Data Schema) → UI 인터랙션(UI Spec)
:::

명세가 견고하면 에이전트는 결코 길을 잃지 않습니다. 자신이 무엇을 만들어야 하는지뿐만 아니라, "무엇을 건드리지 말아야 하는지"를 명확히 인지하기 때문입니다.

## 새로운 엔지니어링 표준: 컴파일러로서의 AI

이 책은 단순히 "클로드에게 코딩 잘 시키는 프롬프트 팁"을 알려주는 책이 아닙니다. 코드를 손으로 한 줄씩 타이핑하던 전통적인 소프트웨어 공학의 시대를 지나, **명세를 설계하고 에이전트를 오케스트레이션하는** 새로운 시대의 기술 표준(Engineering Standard)을 다루는 안내서입니다.

<!--figure: book-map | 원리가 문서를 낳고, 문서가 실행을 지시하고, 실행이 층으로 쌓인다. 이 책은 이 순서로만 읽힌다.-->

::: {.callout}
[이 책의 구성]{.label}

**제1부 · 원리** — 코드가 아니라 명세를 시스템의 원본으로 삼는다는 것이 무엇을 뜻하는지 규명합니다. 헌법적 명세와 단일 진실 공급원, 코드 리뷰 이전의 명세 승인, 그리고 컨텍스트를 단계로 잘라 통제하는 법.

**제2부 · 무엇을 쓰는가** — 네 개의 명세 문서(PRD, Architecture, Data Schema, UI Spec)를 실제 템플릿과 함께 바닥부터 작성합니다. 그리고 네 문서가 서로 어긋나지 않는지 교차 검증하는 법까지.

**제3부 · 어떻게 실행하는가** — 다섯 가지 에이전트 워크플로우(체이닝, 라우팅, 병렬화, 오케스트레이터-워커, 평가기-최적화기)와, 명세를 현실의 파일·데이터베이스·네트워크에 연결하는 Model Context Protocol(MCP)을 다룹니다.

**제4부 · 어떻게 올리는가** — 공개 API 하나로 재현할 수 있는 **공시 아카이브**를 [Phase 1]부터 [Phase 3]까지 직접 빌드합니다. 수집과 정규화, 스키마와 검색, 컨테이너 배포와 외부 개방. 각 장 끝에는 실제로 운용 중인 시스템에서 겪은 장애 기록이 붙습니다.
:::

## 명세를 장악하는 자가 시스템을 지배한다

소프트웨어 엔지니어의 역할이 바뀌고 있습니다. 문법을 외우고, 세미콜론을 찍고, 라이브러리 함수 이름을 검색하느라 밤을 지새우던 시대는 저물고 있습니다. 이제 엔지니어의 핵심 경쟁력은 코드를 얼마나 빨리 치느냐가 아니라, **"비즈니스 문제를 얼마나 명확한 데이터 구조와 명세로 번역해낼 수 있는가"** 에 달려 있습니다.

코드를 에이전트에게 온전히 위임하고, 여러분은 시스템의 헌법을 세우는 아키텍트의 자리로 올라서십시오.

앤스로픽의 엔지니어들이 일하는 방식, 그 표준화된 여정을 지금 시작합니다.
