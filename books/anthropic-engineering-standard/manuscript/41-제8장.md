## 명세 슬라이싱과 프로젝트 뼈대

이제 앞의 일곱 장에서 세운 것을 실제로 돌려볼 차례입니다. 우리가 만들 것은 **공시 아카이브**입니다. 금융감독원 전자공시(DART)가 공개하는 OpenAPI로 기업 공시를 수집하고, 재무 수치를 정규화해서, 검색 가능한 구조로 쌓는 시스템입니다.

이 도메인을 고른 데는 이유가 있습니다. 마크다운 뷰어나 할 일 목록은 값이 틀려도 아무 일이 일어나지 않습니다. 그래서 명세가 왜 필요한지 설명할 수가 없습니다. 반면 공시 데이터는 **숫자 하나가 틀리면 그 위에 쌓은 모든 판단이 틀립니다.** 명세 주도 개발이 왜 필요한지를 도메인 자체가 증명해 주는 자리입니다.

준비물은 단순합니다. DART OpenAPI 인증키(무료), 파이썬 또는 노드 런타임, 노트북 한 대. 데이터베이스도 클라우드도 Phase 1에서는 쓰지 않습니다.

- **포함** — OpenAPI 클라이언트, 공시 목록·원문 조회, 재무 항목 정규화, 단위 테스트.
- **제외** — 데이터베이스, 검색 엔진, 알림, 배포. 전부 [Phase 2] 이후다.

레이어는 셋으로 가릅니다. **API 클라이언트**(네트워크와 재시도를 아는 층), **정규화 코어**(외부 의존이 0인 순수 함수), **테스트**. 이 경계가 흐려지면 나중에 코어를 테스트할 때마다 네트워크가 필요해집니다.


## 실패를 먼저 명세한다 — DART API 클라이언트

여기서 이 책의 순서 하나를 뒤집습니다.

보통 API 클라이언트를 만들라고 하면 에이전트는 **성공 경로**부터 씁니다. 요청을 보내고, 200이면 JSON을 파싱하고, 값을 돌려줍니다. 그리고 마지막에 `try/except`를 하나 둘러 "에러가 나면 로그를 남긴다"로 마감합니다.

실제로 돌아가는 시스템의 클라이언트는 정반대로 생겼습니다. **먼저 오는 것은 파싱이 아니라 실패의 분류입니다.**

### 세 부류로 가르지 않으면 시스템이 거짓말을 한다

DART API는 HTTP 200을 돌려주면서 본문의 `status` 필드로 결과를 알려줍니다. 이 코드들을 한 덩어리로 "에러"라고 처리하면 시스템이 조용히 망가집니다.

::: {.formula}
[에러 코드를 세 부류로 가른다]{.label}

- **입력 오류 — `010` `011` `100` `901`** · 인증키가 잘못되었거나 파라미터가 틀렸다. **즉시 실패시킨다.** 재시도는 호출 예산만 태운다.
- **데이터 없음 — `013`** · **에러가 아니다.** 그 기업의 그 기간에 자료가 없을 뿐이다. 정상 응답으로 반환하고 호출부가 판단하게 한다.
- **일시 장애 — `020` 요청 제한 · `800` 시스템 점검** · 지수 백오프로 재시도한다. 재시도 횟수를 소진하면 그때 실패로 올린다.
:::

가운데 줄이 핵심입니다. **`013`을 에러로 처리하면 자료가 없는 정상 종목이 장애로 둔갑합니다.** 대시보드에는 실패 건수가 치솟고, 로그는 빨갛게 물들고, 엔지니어는 있지도 않은 네트워크 문제를 찾아 하루를 씁니다. 그런데 시스템은 정확히 명세대로 동작하고 있습니다 — 명세가 "데이터 없음"과 "가져오기 실패"를 구분하지 않았을 뿐입니다.

자연어 명세는 이 둘을 절대 구분해 주지 않습니다. "공시를 조회한다"라고 쓰면 에이전트는 조회가 성공하거나 실패하는 두 가지 세계만 상상합니다. **세 번째 상태를 명세에 적어 넣는 것은 사람의 일입니다.**

<!--figure: dart-error-taxonomy | 실패를 한 덩어리로 두면 시스템은 없는 장애를 만들어 보고한다.-->

### 구현

```python
async def _call_api(endpoint: str, params: dict) -> dict:
    """DART API 공통 호출. 에러 코드별 세분화 처리.
      - 010/011/100/901: 입력 오류 → 즉시 실패 (재시도 불필요)
      - 013: 데이터 없음 → 정상 응답으로 반환 (호출부에서 처리)
      - 020: 요청 제한 초과 → 백오프 재시도 후 다음 폴링 주기로 이연
      - 800: 시스템 점검 → 백오프 재시도
    """
    # 일일 한도 체크 — 예산을 넘으면 호출 자체를 거부한다
    if not api_counter.can_call():
        raise DartAPILimitError()

    for attempt in range(MAX_RETRIES):
        resp = await client.get(url, params=params)
        api_counter.increment()

        if resp.status_code == 200:
            data = resp.json()
            status = data.get("status", "")

            if status in _NO_RETRY_CODES:          # 입력 오류
                raise DartAPIError(status, data.get("message", "입력 오류"))

            if status in _RETRYABLE_CODES:         # 시스템 점검
                if attempt < MAX_RETRIES - 1:
                    await _backoff(attempt)
                    continue
                raise DartAPIError(status, data.get("message", "시스템 점검"))

            return data                            # 000 정상 · 013 데이터 없음

        if attempt < MAX_RETRIES - 1:
            await _backoff(attempt)

    raise DartAPIError("NETWORK", f"{endpoint} 호출 실패 (재시도 소진)")
```

주목할 곳은 마지막에서 두 번째 줄입니다. `000`(정상)과 `013`(데이터 없음)이 **같은 문으로 나갑니다.** 판단은 호출부가 합니다.

### 호출 예산은 코드가 강제한다

DART OpenAPI의 일일 한도는 10,000회입니다. 넉넉해 보이지만 종목 수를 곱하면 금세 바닥납니다.

그래서 첫 줄에 `api_counter.can_call()`이 있습니다. 예산을 넘으면 **요청을 보내기 전에 거부합니다.** 한도를 넘긴 요청은 어차피 `020`으로 돌아오고, 그 왕복이 다시 예산을 태웁니다.

:::::: {.fieldnote}
[현장 노트 — 폴백 하나가 예산을 여덟 배로 튀긴다]{.label}
[2026-08-26 · Dartai/dart-insight/backfill_cash_flows.py]{.src}

현금흐름 데이터를 채우는 배치를 짜다가 알았습니다. `fetch_cash_flow()`에는 요청한 보고서 코드에 자료가 없으면 다른 보고서 코드로 다시 시도하는 폴백이 들어 있었습니다. 편의 기능입니다. 그런데 **자료가 아예 없는 종목에서는 이 폴백이 CFS/OFS 두 갈래 × 보고서 네 종류로 갈라져 호출을 여덟 배로 튀깁니다.** 있지도 않은 자료를 여덟 번 두드리는 셈입니다.

전체 파이프라인이 하루에 약 1,520회를 씁니다. 한도 10,000 중 남는 것은 8,400회. 종목 하나가 여덟 번씩 두드리면 몇백 종목만에 예산이 증발합니다.

그래서 배치에서는 폴백을 껐습니다(`allow_reprt_fallback=False`). 이유는 두 가지였는데, 두 번째가 더 중요했습니다.

> 예산이 예측 가능해야 하고, **연간을 청구했는데 분기 누계가 돌아오면 발생액이 다른 기간을 섞기 때문이다.**

폴백은 호출을 아끼려고 만든 게 아니라 값을 채우려고 만든 것이었는데, 채운 값이 다른 기간의 값이었습니다. 편의 기능이 데이터를 오염시키고 있었습니다.

같은 배치에서 규칙을 하나 더 세웠습니다.

> DART에 자료가 없는 (종목, 연도)를 매일 다시 두드리면 예산이 샌다. 파일에 적어두고 `--retry-misses` 없이는 건너뛴다. **"없다"와 "아직 안 봤다"를 구분한다.**

`013`을 에러로 처리하면 안 되는 이유가 여기서 다시 나옵니다. **"없다"는 결과이고 "못 봤다"는 사고입니다.** 이 둘을 구분하지 않으면 시스템은 매일 없는 것을 다시 찾으러 갑니다.

## 명세가 데이터를 이기지 못하는 자리 — 재무 정규화

이제 코어 레이어입니다. API가 돌려준 원시 항목을 우리 스키마의 값으로 바꾸는 순수 함수들입니다.

여기가 이 장에서 가장 아픈 자리입니다. 스키마도 맞고 타입도 맞는데 **의미가 틀리는** 일이 세 번 일어납니다.

### 함정 A — 연결과 별도가 한 응답에 섞여 온다

DART의 재무제표 API는 연결재무제표(CFS)와 별도재무제표(OFS)를 **한 응답에 함께** 돌려줍니다. `fs_div` 필드로 구분됩니다.

이걸 필터하지 않고 합계를 내면 같은 계정이 두 번 잡히고, 지주회사처럼 연결과 별도의 규모가 크게 다른 기업에서는 값이 완전히 무의미해집니다.

```python
cfs_items = [i for i in items if i.get("fs_div") == "CFS"]
ofs_items = [i for i in items if i.get("fs_div") == "OFS"]
# 연결 우선, 없으면 별도로 폴백
items = cfs_items or ofs_items
```

세 줄입니다. 그런데 이 세 줄은 **명세에 "연결 우선, 없으면 별도"라고 적혀 있지 않으면 에이전트가 쓸 수 없습니다.** 응답 스키마에는 `fs_div`가 그냥 문자열 필드로 있을 뿐이고, 무엇을 우선해야 하는지는 도메인 지식입니다.

### 함정 B — 분기 금액이 회사마다 단독이거나 누계다

이쪽이 훨씬 고약합니다.

분기보고서의 `thstrm_amount`(당기 금액)를 3개월 단독 실적으로 읽는 것이 상식적입니다. 대부분의 기업이 그렇게 냅니다. 그런데 전부는 아닙니다.

::: {.table-wrap}
| 유형 | Q1~Q3 `thstrm_amount` | `thstrm_add_amount` |
|---|---|---|
| **A형** (삼성전자·한화오션·동양 등 9사 중 8사) | 3개월 **단독** | 연초부터 **누계** |
| **B형** (NH프라임리츠) | **누계** | 누계 (앞 칸과 같은 값) |
:::

`thstrm_amount`를 단독값으로 가정하면 **B형 기업에서 누계를 분기 실적으로 오독합니다.** 3분기 리포트를 보고 "이번 분기에 이만큼 벌었다"고 읽었는데 실제로는 연초부터 누적된 값인 것입니다. 성장률도, 전년 동기 대비도, 그 위에 쌓은 모든 판단이 함께 틀립니다.

핵심은 두 번째 칸입니다. **`thstrm_add_amount`는 두 유형 모두에서 일관되게 누계입니다.** 그래서 안전한 순서가 나옵니다.

::: {.formula}
[누계를 정본으로 세우고 차분한다]{.label}

```
누계(Q1..Q3) = thstrm_add_amount   (없으면 thstrm_amount 폴백)
누계(Q4)     = thstrm_amount       (사업보고서 = 연간 누계, add 필드 없음)

단독(Q1) = 누계(Q1)
단독(Qn) = 누계(Qn) - 누계(Q(n-1))    n = 2, 3, 4
```
:::

### 함정 C — 재무상태표는 차분하지 않는다

그런데 방금 세운 규칙을 모든 계정에 적용하면 이번에는 다른 것이 망가집니다.

손익계산서와 현금흐름표는 **유량(flow)** 입니다. 기간 동안 발생한 양이므로 차분이 성립합니다. 재무상태표는 **저량(stock)** 입니다. 특정 시점의 잔액이므로 차분하면 값이 완전히 망가집니다. 3분기 말 자산에서 2분기 말 자산을 빼면 그건 자산이 아니라 자산의 증감입니다.

<!--figure: quarterly-cumulative | 같은 표에서 어떤 줄은 차분해야 하고 어떤 줄은 차분하면 안 된다. 타입이 같아도 의미가 다르기 때문이다.-->

그리고 규칙이 하나 더 필요합니다. 반기 보고서만 내는 리츠처럼 직전 분기 누계가 아예 없는 경우가 있습니다. 이때 차분은 불가능합니다. **값을 지어내지 말고 `None`으로 둡니다.** 여기서 0을 넣거나 직전 값을 재사용하면, 없는 데이터가 있는 데이터의 얼굴을 하고 시스템에 들어옵니다.

### 이 장의 결론 — 스키마에는 타입만으로 부족하다

세 함정이 같은 곳을 가리킵니다.

`thstrm_amount`와 `thstrm_add_amount`는 **타입이 똑같습니다.** 둘 다 문자열로 온 숫자입니다. 어떤 정적 타입 검사도, 어떤 스키마 검증도 이 둘을 구분해 주지 않습니다. 재무상태표의 자산 총계와 손익계산서의 매출액도 타입이 같습니다. 그런데 하나는 차분하면 안 되고 하나는 차분해야 합니다.

::: {.callout}
데이터 스키마에 **타입만 적으면 부족합니다.** 이 값이 유량인지 저량인지, 단독인지 누계인지, 없을 때 무엇으로 두는지 — **의미 단위를 적어야** 에이전트가 차분해도 되는지 안 되는지 압니다.

타입 무결성은 의미 무결성을 보장하지 않습니다.
:::

이 표는 추론이 아니라 열 개 회사를 직접 열어 대조한 결과입니다. 9사 중 8사가 A형이었고 NH프라임리츠 하나가 B형이었습니다. 표본이 작으니 "대부분 A형"이라고 말할 수는 있어도 "A형이다"라고 말할 수는 없습니다. **그래서 예외가 하나뿐이어도 규약은 예외를 기준으로 세웠습니다.**

검증법도 함께 세웠습니다. **단독 4분기의 합이 연간과 같아야 합니다.** 삼성전자 2024년으로 맞춰봤습니다 — 71.9 / 74.1 / 79.1 / 75.8, 합계 300.9조. 맞았습니다.

그런데 이 규약을 정본 모듈에 구현하고 나서도, 옛 코드 경로 하나가 아직 고쳐지지 않았습니다. 그래서 프로젝트 헌법 문서에 이렇게 적어두었습니다.

> 정본 구현은 `modules/financial_timeseries.py`. ⚠️ `dart_client._fetch_single_quarter`는 아직 Q1~Q3에서 `thstrm_amount`를 단독으로 읽어 **B형 기업에서 오독한다**(미수정).

## Phase 1 마감 — 기계적 검증과 커밋

Phase 1이 끝났다고 선언하는 기준은 "돌려보니 잘 되는 것 같다"가 아닙니다.

::: {.formula}
[이 단계의 평가기]{.label}

1. **타입·린트** — 코어 레이어에 외부 임포트가 없는지, 순환 참조가 없는지.
2. **단독 4분기 합 == 연간** — 함정 B의 규약이 실제로 성립하는지 실제 기업 데이터로 대조.
3. **`013` 경로** — 자료 없는 (종목, 연도)를 넣었을 때 예외가 아니라 빈 결과가 돌아오는지.
4. **예산 상한** — 호출 상한을 넘기면 배치가 멈추고, 다음 실행이 그 지점부터 재개되는지.
:::

2번이 이 단계에서 가장 중요한 테스트입니다. 파서가 문법적으로 잘 도는지가 아니라 **값이 맞는지**를 묻기 때문입니다. 그리고 이 테스트는 사람이 판정하지 않습니다. 합이 맞거나 틀리거나 둘 중 하나입니다.

::: {.callout}
Phase 1의 결과물은 대화창의 기억이 아니라 커밋된 파일로 남습니다. 세션을 닫고 컨텍스트를 비운 뒤, [Phase 2]만 주입해 새 세션을 엽니다.
:::
