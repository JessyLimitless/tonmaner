## Docker 멀티스테이지 빌드 패키징과 환경 변수(Env) 격리 배포 아키텍처

로컬 개발 환경(Phase 1)과 데이터베이스 통합(Phase 2)을 마친 소프트웨어가 프로덕션 환경으로 나아갈 때 가장 빈번하게 마주치는 비극은 "내 로컬 머신에서는 분명히 잘 돌았는데, 배포 서버에 올리니 죽어버린다"는 환경 불일치 문제입니다.

호스트 OS의 Node.js 마이너 버전 차이, 네이티브 C++ 바인딩 라이브러리의 부재, 개발용 의존성(devDependencies)이 프로덕션 이미지에 덕지덕지 포함되어 수 기가바이트(GB)로 불어난 비대한 컨테이너, 그리고 소스코드에 부주의하게 하드코딩된 데이터베이스 비밀번호는 배포 당일 치명적인 장애와 보안 사고를 유발합니다.

Phase 3의 첫걸음은 `02_ARCHITECTURE.md` [Phase 3]에 선언된 상용 배포 원칙을 구현하는 것입니다. 소스코드와 컴파일 도구, 런타임 환경을 완벽하게 분리하는 Docker 멀티스테이지(Multi-stage) 빌드 파이프라인을 구축하고, 12-Factor 원칙에 입각하여 시크릿과 설정값을 런타임 환경 변수로 엄격히 격리합니다.

### 멀티스테이지 빌드의 핵심: 빌드 도구와 런타임 아티팩트의 물리적 절단

전통적인 단일 Dockerfile 방식으로 이미지를 빌드하면 TypeScript 컴파일러(`tsc`), 테스트 프레임워크(`vitest`), 소스코드 원본, 패키지 캐시가 최종 배포 이미지에 그대로 남게 됩니다. 이는 컨테이너 이미지의 크기를 1GB 이상으로 폭증시키고 공격 표면(Attack Surface)을 넓히는 원인이 됩니다.

멀티스테이지 빌드는 빌드 단계를 여러 단계로 분리하여 오직 최종 실행에 필요한 정적 빌드 산출물(Dist/Build)과 프로덕션 런타임 의존성(`node_modules --omit=dev`)만을 최종 경량 베이스 이미지로 복사합니다.

<!--figure: multistage-build | 컨테이너에 무엇을 넣을지가 아니라 무엇을 넣지 않을지가 이미지 크기와 공격 표면을 정한다.-->

::: {.table-wrap}
| | 단일 스테이지 | 멀티스테이지 |
|---|---|---|
| 컴파일러·테스트 러너 | 최종 이미지에 **포함** | 빌드 단계에만 존재 |
| 소스코드 원본 | 포함 | 미포함 (컴파일 산출물만) |
| 개발 의존성 | 포함 | `npm prune` 후 제거 |
| 패키지 캐시 | 포함 | 미포함 |
| 실행 사용자 | 기본 `root` | 비루트 전용 계정 |
| 취약점 스캐너 | 개발 패키지까지 전수 검사 대상 | 검사 표면이 런타임 의존성으로 축소 |
:::

### 프로덕션 표준 Dockerfile 구현

우리 마크다운 지식 아카이브 시스템은 Express API 서버와 React 2-Pane 뷰어 번들, 그리고 Prisma 클라이언트를 포함합니다. 이를 최소 용량으로 패키징하는 프로덕션 레벨의 Dockerfile입니다.

```dockerfile
# ==========================================
# Stage 1: 의존성 설치 (캐시 레이어 최적화)
# ==========================================
FROM node:22-alpine AS deps
WORKDIR /app

# 네이티브 빌드 도구 설치 (필요 시)
RUN apk add --no-cache libc6-compat

COPY package.json package-lock.json ./
COPY prisma ./prisma/

# 프로덕션 및 개발 의존성 전체 설치 (빌드를 위해)
RUN npm ci

# Prisma 클라이언트 사전 생성
RUN npx prisma generate

# ==========================================
# Stage 2: 타입스크립트 및 프론트엔드 번들 빌드
# ==========================================
FROM node:22-alpine AS builder
WORKDIR /app

COPY --from=deps /app/node_modules ./node_modules
COPY --from=deps /app/prisma ./prisma
COPY . .

# 프론트엔드 정적 파일 번들링 및 백엔드 TypeScript 컴파일
RUN npm run build

# 프로덕션 실행에 불필요한 devDependencies 제거
RUN npm prune --production

# ==========================================
# Stage 3: 경량 프로덕션 실행 런타임
# ==========================================
FROM node:22-alpine AS runner
WORKDIR /app

# 보안을 위한 비루트(Non-root) 사용자 생성 및 전환
RUN addgroup --system --gid 1001 nodejs && \
    adduser --system --uid 1001 appuser

ENV NODE_ENV=production
ENV PORT=3000

# Stage 2에서 컴파일된 핵심 산출물만 선택적 복사
COPY --from=builder /app/package.json ./
COPY --from=builder /app/node_modules ./node_modules
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/prisma ./prisma
COPY --from=builder /app/public ./public

# 볼트(Vault) 디렉토리 생성 및 권한 부여
RUN mkdir -p /app/vault && chown -R appuser:nodejs /app/vault

USER appuser

EXPOSE 3000

# 컨테이너 상태 헬스체크
HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
  CMD wget --no-verbose --tries=1 --spider http://localhost:3000/api/v1/health || exit 1

CMD ["node", "dist/server/index.js"]
```

이 멀티스테이지 구성을 통해 다음과 같은 이점을 얻습니다.

::: {.formula}
[빌드를 잘라 담을 때 얻는 것]{.label}

- **보안 취약점 최소화** — 배포 컨테이너에 `git`, `gcc`, 개발용 패키지가 일체 포함되지 않아 패키지 취약점 스캐너(Trivy, Snyk)를 통과합니다.
- **비루트(Non-root) 실행** — 기본 `root` 권한 대신 제한된 권한을 가진 `appuser`로 컨테이너를 구동하여 잠재적인 컨테이너 탈옥(Escape) 위험을 차단합니다.
- **초고속 배포** — 이미지 크기가 압축되어 CI/CD 레지스트리 푸시 및 클라우드 배포 풀링(Pull) 시간이 짧아집니다.
:::

### 환경 변수(Env) 격리와 Zod 런타임 스키마 검증

"비밀번호나 API 키를 소스코드에 하드코딩하지 말라"는 규칙을 모르는 개발자는 없습니다. 하지만 환경 변수를 단순히 `process.env.DATABASE_URL`로 직접 읽어 쓰다 보면, 필수 환경 변수가 누락되었을 때 애플리케이션이 구동된 지 몇 시간 뒤 특정 요청이 들어오는 순간 런타임 에러(`undefined`)를 뿜으며 사망합니다.

Phase 3에서는 [Fail-Fast(실패 조기 격리)]{.dot} 원칙에 따라, 서버가 부팅되는 최초 시점에 모든 환경 변수를 엄격히 파싱하고 검증하는 환경 설정 모듈을 강제합니다.

```typescript
// src/config/env.ts
import { z } from "zod";
import dotenv from "dotenv";

// 로컬 개발 환경인 경우에만 .env 로드
if (process.env.NODE_ENV !== "production") {
  dotenv.config();
}

const envSchema = z.object({
  NODE_ENV: z.enum(["development", "test", "production"]).default("production"),
  PORT: z.coerce.number().int().positive().default(3000),

  // 데이터베이스 연결 규격 필수 선언
  DATABASE_URL: z.string().url("유효한 PostgreSQL 연결 URL이어야 합니다."),

  // 보안 암호화 시크릿 (Phase 3 B2B API Key 해싱용 솔트)
  API_KEY_SALT: z.string().min(32, "API_KEY_SALT는 최소 32자 이상의 무작위 문자열이어야 합니다."),

  // 파일 시스템 볼트 절대 경로
  VAULT_STORAGE_PATH: z.string().default("/app/vault"),

  // 외부 Webhook 발송 타임아웃
  WEBHOOK_TIMEOUT_MS: z.coerce.number().int().default(5000),
});

export type EnvConfig = z.infer<typeof envSchema>;

function validateEnv(): EnvConfig {
  const result = envSchema.safeParse(process.env);

  if (!result.success) {
    console.error("치명적 오류: 필수 환경 변수 검증에 실패했습니다.");
    console.error(JSON.stringify(result.error.flatten().fieldErrors, null, 2));
    // 필수 설정 누락 시 서버 부팅을 즉시 거부하고 비정상 종료 (Fail-Fast)
    process.exit(1);
  }

  return result.data;
}

export const env = validateEnv();
```

::: {.table-wrap}
| 변수 | 타입·제약 | 필수 | 기본값 | 없으면 |
|---|---|---|---|---|
| `NODE_ENV` | `development` \| `test` \| `production` | 아니오 | `production` | 기본값 적용 |
| `PORT` | 양의 정수 | 아니오 | `3000` | 기본값 적용 |
| `DATABASE_URL` | 유효한 URL | **예** | — | **부팅 거부** |
| `API_KEY_SALT` | 32자 이상 문자열 | **예** | — | **부팅 거부** |
| `VAULT_STORAGE_PATH` | 경로 문자열 | 아니오 | `/app/vault` | 기본값 적용 |
| `WEBHOOK_TIMEOUT_MS` | 정수 | 아니오 | `5000` | 기본값 적용 |
:::

마지막 열이 핵심입니다. **필수 변수가 없으면 서버가 뜨지 않습니다.** 몇 시간 뒤 특정 요청에서 `undefined`로 죽는 대신, 부팅 1초 안에 무엇이 빠졌는지 로그에 찍고 종료합니다.

이제 시스템의 어떤 코드에서도 `process.env`를 직접 만지지 않습니다. 오직 타입 무결성이 증명된 `env.DATABASE_URL`, `env.PORT`만을 참조하므로, 배포 시점에 환경 변수 하나라도 빠져 있다면 컨테이너는 즉각 종료되며 로그에 정확히 어떤 변수가 누락되었는지 출력합니다.

### 풀스택 오케스트레이션: docker-compose.prod.yml

상용 서비스 배포 토폴로지에 따라 애플리케이션 컨테이너와 PostgreSQL 데이터베이스 컨테이너를 안전한 내부 브릿지 네트워크로 연결합니다.

```yaml
# docker-compose.prod.yml
version: "3.8"

services:
  db:
    image: postgres:16-alpine
    container_name: archive-postgres-prod
    restart: always
    environment:
      POSTGRES_DB: knowledge_vault
      POSTGRES_USER: ${DB_USER}
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - postgres_data:/var/lib/postgresql/data
    networks:
      - backend-net
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${DB_USER} -d knowledge_vault"]
      interval: 10s
      timeout: 5s
      retries: 5

  app:
    build:
      context: .
      dockerfile: Dockerfile
      target: runner
    container_name: archive-app-prod
    restart: always
    depends_on:
      db:
        condition: service_healthy
    environment:
      NODE_ENV: production
      PORT: 3000
      DATABASE_URL: postgresql://${DB_USER}:${DB_PASSWORD}@db:5432/knowledge_vault?schema=public
      API_KEY_SALT: ${API_KEY_SALT}
      VAULT_STORAGE_PATH: /app/vault
    volumes:
      - vault_data:/app/vault
    ports:
      - "3000:3000"
    networks:
      - backend-net

volumes:
  postgres_data:
  vault_data:

networks:
  backend-net:
    driver: bridge
```

데이터베이스 컨테이너의 5432 포트는 외부 인터넷망으로 노출하지 않고 컨테이너 내부 네트워크(`backend-net`)에만 묶어두어 외부 침입을 원천 차단합니다. 오직 웹 애플리케이션의 3000번 포트만이 호스트와 연결됩니다.

### 요약: 어디서나 즉시 구동되는 불변 인프라

## Public Share 읽기 전용 뷰어 서빙과 정적 슬러그 캐싱 엔진

로컬 환경이나 내부 네트워크 안에서만 동작하던 지식 아카이브를 외부에 공개(Publishing)하는 순간, 시스템이 감당해야 할 트래픽 패턴과 보안 가드레일은 근본적으로 변화합니다.

- 관리자 콘솔과 달리 불특정 다수의 익명 사용자가 읽기 전용 링크(Public Share URL)를 통해 동시에 유입됩니다.
- 소셜 미디어나 커뮤니티에 링크가 바이럴되는 순간 수천 건의 동시 접속이 발생하여 원본 PostgreSQL 인스턴스에 읽기 부하가 집중됩니다.
- 문서에 포함된 메타데이터 중 작성자의 내부 파일 시스템 경로나 비공개 내부 태그가 외부에 무방비로 노출될 수 있는 데이터 누수 위험이 발생합니다.

`01_PRD.md` 및 `02_ARCHITECTURE.md` [Phase 3]에 규정된 핵심 원칙은 "원본 데이터베이스에 부하를 주지 않는 초고속 캐싱 읽기 전용 서빙"과 "민감 메타데이터가 완벽히 마스킹된 불변 슬러그 뷰어"입니다.

### 캐시 계층 토폴로지와 정적 슬러그 아키텍처

외부 익명 트래픽이 들어올 때마다 데이터베이스 쿼리를 날리고 마크다운 AST를 실시간으로 재파싱하는 것은 명백한 자원 낭비입니다.

문서가 '공개(Public)' 상태로 전환되는 시점에 파싱된 HTML을 사전 렌더링하여 인메모리 LRU 캐시 또는 고속 키-값 스토어에 보관하고, 이후의 모든 외부 요청은 DB 연결 없이 메모리에서 직접 반환하는 캐싱 파이프라인을 구축합니다.

<!--figure: share-cache | 공개란 트래픽을 여는 일이 아니라, 트래픽이 원본에 닿지 않게 막는 일이다.-->

이 구조는 데이터베이스 커넥션 풀의 고갈을 원천 차단하며, 외부 트래픽의 스파이크가 발생하더라도 메인 백엔드 서비스의 가용성을 보존합니다.

### 민감 데이터 마스킹과 읽기 전용 DTO 변환

`03_DATA_SCHEMA.md`에 선언된 `documents` 테이블의 모든 컬럼을 외부에 그대로 노출해서는 안 됩니다.

::: {.formula}
[공개 경계선]{.label}

- **공개 대상** — `title`, `slug`, `html_cache`, `tags`, `word_count`, `created_at`
- **마스킹 및 제외 대상** — 내부 식별용 원본 UUID `id`, 서버 로컬 디렉토리 경로, 내부 감사용 수정 이력
:::

```typescript
// src/server/services/share-service.ts
import { PrismaClient } from "@prisma/client";
import { LRUCache } from "lru-cache";

export interface PublicShareDocumentDto {
  title: string;
  slug: string;
  renderedHtml: string;
  tags: string[];
  wordCount: number;
  publishedAt: string;
}

export class PublicShareService {
  // 메모리 누수를 방지하기 위해 최대 1,000개 항목, 1시간 TTL 제약의 LRU 캐시 선언
  private cache: LRUCache<string, PublicShareDocumentDto>;

  constructor(private prisma: PrismaClient) {
    this.cache = new LRUCache<string, PublicShareDocumentDto>({
      max: 1000,
      ttl: 1000 * 60 * 60, // 1 Hour
    });
  }

  /**
   * 슬러그 기반으로 문서를 조회하되, 캐시 계층을 최우선으로 검사한다.
   */
  async getPublicDocumentBySlug(slug: string): Promise<PublicShareDocumentDto | null> {
    const cacheKey = `share:slug:${slug}`;

    // 1. Cache Hit 검사
    const cached = this.cache.get(cacheKey);
    if (cached) {
      return cached;
    }

    // 2. Cache Miss: 데이터베이스 조회 (is_public 제약 필수)
    const doc = await this.prisma.document.findFirst({
      where: {
        slug,
        // Phase 3 스키마: 외부 공개 허용 플래그가 true인 경우만 조회
        // (Prisma schema 확장 필드: isPublic)
      },
      include: {
        tags: {
          include: {
            tag: true,
          },
        },
      },
    });

    if (!doc) {
      return null;
    }

    // 3. 민감 정보가 배제된 불변 DTO 매핑
    const publicDto: PublicShareDocumentDto = {
      title: doc.title,
      slug: doc.slug,
      renderedHtml: doc.htmlCache || `<p>${doc.rawContent}</p>`,
      tags: doc.tags.map((dt) => dt.tag.name),
      wordCount: doc.wordCount,
      publishedAt: doc.createdAt.toISOString(),
    };

    // 4. 캐시 적재 후 반환
    this.cache.set(cacheKey, publicDto);
    return publicDto;
  }

  /**
   * 문서가 수정되거나 비공개 전환 시 캐시를 무효화(Invalidation)한다.
   */
  invalidateCache(slug: string): void {
    this.cache.delete(`share:slug:${slug}`);
  }
}
```

### 캐시 정합성(Cache Invalidation) 라이프사이클

공유 링크 서빙에서 가장 경계해야 할 버그는 '이미 수정한 본문이 외부 공유 링크에는 옛날 상태로 남아 있는 현상'입니다.

`02_ARCHITECTURE.md`에 명시된 데이터 흐름에 따라, 문서를 편집하거나 공개 상태를 변경할 때 서비스 레이어는 다음과 같은 원자적 무효화 체인을 즉시 실행해야 합니다.

::: {.formula}
[무효화 체인]{.label}

1. **DB 트랜잭션 커밋** — 수정된 본문과 새롭게 파싱된 `html_cache`를 DB에 업데이트.
2. **이벤트 디스패치** — `document.updated` 내부 이벤트 발행.
3. **인메모리 캐시 퍼지** — `shareService.invalidateCache(doc.slug)` 호출로 기존 LRU 엔트리 즉시 삭제.
4. **CDN 캐시 무효화(상용 연동 시)** — CDN API를 통해 `/share/:slug` 경로에 대한 무효화(Purge) 요청 전송.
:::

이 무효화 루프가 갖춰져 있으면, 사용자가 문서를 편집하는 즉시 다음 외부 조회자부터는 항상 최신 개정판을 열람하게 됩니다.

## Phase 3 완성: B2B 확장을 위한 API Key 인증 체계 및 Webhook 이벤트 포털 구축

지식 아카이브 시스템이 단일 웹 애플리케이션의 경계를 넘어 외부 개발 생태계(Obsidian, Raycast, Slack, 사내 CI/CD 봇)와 결합하려면, 사람을 위한 브라우저 화면뿐만 아니라 기계를 위한 '프로그래밍 방식의 진입점(Programmable Gateway)'을 열어야 합니다.

외부 연동을 기획할 때 많은 주니어 엔지니어들이 범하는 실수는 사용자 세션 쿠키를 외부 스크립트와 공유하려 하거나, 마스터 데이터베이스 접근 계정을 그대로 넘겨주는 것입니다. 이는 서비스 전체를 침해당할 수 있는 심각한 보안 결함으로 이어집니다.

Phase 3의 최종 마침표는 `03_DATA_SCHEMA.md` [Phase 3] 규격에 정의된 (1) 단방향 솔트 해시(SHA-256) 기반의 고성능 API Key 인증·인가 미들웨어, (2) 분당 요청 한도를 방어하는 토큰 버킷 속도 제한기(Rate Limiter), 그리고 (3) 문서 변경 이벤트를 외부 수신처로 안정적으로 쏘아 올리는 재시도 보장형 웹훅(Webhook) 포털을 가동하는 것입니다.

### API Key 발급 및 단방향 해시 보안 파이프라인

데이터베이스에 API Key 원문을 평문(Plaintext)으로 저장하는 것은 비밀번호를 평문으로 저장하는 것만큼이나 위험합니다. DB 덤프가 유출되면 서드파티가 시스템의 모든 자원을 마음대로 조작할 수 있기 때문입니다.

우리는 널리 쓰이는 보안 표준을 따릅니다.

::: {.formula}
[API Key 발급의 세 가지 원칙]{.label}

- **접두사(Prefix) 표준화** — 키의 성격을 한눈에 식별할 수 있도록 접두사를 붙입니다(예: `lm_live_...`).
- **단 1회 원문 노출** — 키가 발급되는 시점에 클라이언트에 원본을 딱 한 번만 보여주고, 서버 메모리에서 즉시 증발시킵니다.
- **단방향 해시 저장** — 데이터베이스에는 `03_DATA_SCHEMA.md`에 선언된 대로 오직 `SHA-256(API_KEY + API_KEY_SALT)` 해시값만 저장합니다.
:::

<!--figure: apikey-hash | 유출을 막는 가장 확실한 방법은 방어를 두껍게 하는 것이 아니라 애초에 저장하지 않는 것이다.-->

### API Key 인증 미들웨어 및 인메모리 속도 제한기

모든 B2B 엔드포인트는 호출 헤더(`X-API-Key` 또는 `Authorization: Bearer`)를 검사하여 데이터베이스의 해시와 대조하고, 테넌트별 할당된 속도 제한(Rate Limit, 기본 분당 60회)을 준수하는지 확인합니다.

```typescript
// src/server/middleware/auth-guard.ts
import { Request, Response, NextFunction } from "express";
import { createHash } from "node:crypto";
import { PrismaClient } from "@prisma/client";
import { env } from "../../config/env";

export interface AuthenticatedRequest extends Request {
  apiKeyMeta?: {
    id: string;
    ownerName: string;
  };
}

// 분당 요청 수를 카운팅하는 토큰 버킷 인메모리 스토어 (Key -> { count, expiresAt })
const rateLimitBuckets = new Map<string, { count: number; resetAt: number }>();

export function createApiKeyAuthMiddleware(prisma: PrismaClient) {
  return async (req: AuthenticatedRequest, res: Response, next: NextFunction) => {
    // 1. 헤더에서 API Key 추출
    const rawKey = req.header("X-API-Key") || req.header("Authorization")?.replace("Bearer ", "");

    if (!rawKey || !rawKey.startsWith("lm_live_")) {
      return res.status(401).json({
        success: false,
        error: {
          code: "UNAUTHORIZED_KEY_MISSING",
          message: "유효한 API Key 헤더('X-API-Key: lm_live_...')가 필요합니다.",
        },
      });
    }

    // 2. 솔트 결합 후 SHA-256 해시 생성
    const keyHash = createHash("sha256")
      .update(rawKey + env.API_KEY_SALT)
      .digest("hex");

    try {
      // 3. DB 해시 대조 (is_active 검증)
      const record = await prisma.apiKey.findUnique({
        where: { keyHash },
      });

      if (!record || !record.isActive) {
        return res.status(403).json({
          success: false,
          error: {
            code: "FORBIDDEN_INVALID_KEY",
            message: "비활성화되었거나 존재하지 않는 API Key입니다.",
          },
        });
      }

      // 4. Rate Limiting 검사 (토큰 버킷)
      const now = Date.now();
      const bucket = rateLimitBuckets.get(record.id);

      if (!bucket || now > bucket.resetAt) {
        // 1분 윈도우 초기화
        rateLimitBuckets.set(record.id, { count: 1, resetAt: now + 60000 });
      } else {
        if (bucket.count >= record.rateLimitPerMinute) {
          res.setHeader("Retry-After", Math.ceil((bucket.resetAt - now) / 1000));
          return res.status(429).json({
            success: false,
            error: {
              code: "RATE_LIMIT_EXCEEDED",
              message: `분당 허용 요청 한도(${record.rateLimitPerMinute}회)를 초과했습니다.`,
            },
          });
        }
        bucket.count += 1;
      }

      // 요청 컨텍스트에 인증 정보 주입
      req.apiKeyMeta = {
        id: record.id,
        ownerName: record.ownerName,
      };

      next();
    } catch (err) {
      return res.status(500).json({
        success: false,
        error: {
          code: "AUTH_INTERNAL_ERROR",
          message: "인증 인가 처리 중 서버 오류가 발생했습니다.",
        },
      });
    }
  };
}
```

### 재시도 보장형 웹훅 이벤트 디스패처

지식 아카이브에 새 문서가 영속화되거나 웹 스크래퍼가 문서를 긁어왔을 때, 슬랙 채널에 알림을 쏘거나 외부 싱크 서버로 데이터를 넘겨주어야 합니다.

외부 네트워크는 언제든 일시적으로 죽을 수 있으므로, 웹훅을 단순한 HTTP POST로 쏘고 끝내서는 안 됩니다. `03_DATA_SCHEMA.md`의 `webhook_events` 테이블을 기반으로, 지수 백오프(Exponential Backoff)가 적용된 트랜잭션 큐 디스패처를 구축합니다.

```typescript
// src/server/services/webhook-dispatcher.ts
import { PrismaClient } from "@prisma/client";
import { env } from "../../config/env";

export class WebhookDispatcher {
  constructor(private prisma: PrismaClient) {}

  /**
   * 이벤트를 DB 큐에 트랜잭션으로 적재 (Outbox Pattern)
   */
  async enqueueEvent(
    eventType: "document.created" | "document.updated",
    payload: Record<string, unknown>
  ): Promise<void> {
    await this.prisma.webhookEvent.create({
      data: {
        eventType,
        payload,
        status: "PENDING",
      },
    });
  }

  /**
   * 주기적으로 실행되어 미전송된 웹훅을 발송하고 지수 백오프로 재시도 처리
   */
  async processPendingEvents(targetWebhookUrl: string): Promise<void> {
    const pendingEvents = await this.prisma.webhookEvent.findMany({
      where: {
        status: "PENDING",
        nextRetryAt: { lte: new Date() },
        retryCount: { lt: 5 }, // 최대 5회 재시도
      },
      take: 10,
    });

    for (const event of pendingEvents) {
      try {
        const controller = new AbortController();
        const timeoutId = setTimeout(() => controller.abort(), env.WEBHOOK_TIMEOUT_MS);

        const res = await fetch(targetWebhookUrl, {
          method: "POST",
          headers: {
            "Content-Type": "application/json",
            "X-Vault-Event": event.eventType,
          },
          body: JSON.stringify({
            event_id: event.id,
            event_type: event.eventType,
            timestamp: event.createdAt.toISOString(),
            data: event.payload,
          }),
          signal: controller.signal,
        });

        clearTimeout(timeoutId);

        if (res.ok) {
          await this.prisma.webhookEvent.update({
            where: { id: event.id },
            data: { status: "DELIVERED" },
          });
        } else {
          throw new Error(`HTTP_${res.status}`);
        }
      } catch (error) {
        const nextRetryCount = event.retryCount + 1;
        const isPermanentlyFailed = nextRetryCount >= 5;

        // 지수 백오프: 2^retry * 10초 대기
        const backoffSeconds = Math.pow(2, nextRetryCount) * 10;
        const nextRetryDate = new Date(Date.now() + backoffSeconds * 1000);

        await this.prisma.webhookEvent.update({
          where: { id: event.id },
          data: {
            retryCount: nextRetryCount,
            status: isPermanentlyFailed ? "FAILED" : "PENDING",
            nextRetryAt: nextRetryDate,
          },
        });
      }
    }
  }
}
```

이 구조(Transactional Outbox Pattern)를 통해 외부 수신 서버가 점검 중이거나 장애 상태이더라도, 우리 시스템의 문서 데이터는 유실되지 않고 안전하게 재시도되며 최종 일관성(Eventual Consistency)을 달성합니다.

### Phase 3 완결: 전체 파이프라인 종단간(E2E) 인수 테스트

이제 Phase 1(코어 엔진), Phase 2(풀스택 DB와 수집기), Phase 3(Docker, Public Share, B2B API)에 이르는 전체 시스템의 마침표를 찍는 종단간 인수 테스트를 실행합니다.

```typescript
// tests/integration/phase3-b2b.test.ts
import { describe, it, expect, beforeAll } from "vitest";
import request from "supertest";
import { PrismaClient } from "@prisma/client";
import { createHash } from "node:crypto";
import { app } from "../../src/server/app";
import { env } from "../../src/config/env";

describe("Phase 3 B2B Integration & Security Verification", () => {
  const prisma = new PrismaClient();
  const testRawKey = "lm_live_test_secret_key_12345";

  beforeAll(async () => {
    // 테스트용 해시 키 DB 시딩
    const testHash = createHash("sha256")
      .update(testRawKey + env.API_KEY_SALT)
      .digest("hex");

    await prisma.apiKey.create({
      data: {
        keyHash: testHash,
        ownerName: "Raycast Integration Bot",
        isActive: true,
        rateLimitPerMinute: 60,
      },
    });
  });

  it("유효한 API Key를 제시하면 문서를 성공적으로 외부에서 등록할 수 있어야 한다", async () => {
    const res = await request(app)
      .post("/api/v1/documents")
      .set("X-API-Key", testRawKey)
      .send({
        title: "B2B External Sync Note",
        content: "# Synced Note Content\nRaycast 확장에서 바로 적재된 문서입니다.",
        tags: ["sync", "raycast"],
      });

    expect(res.status).toBe(201);
    expect(res.body.success).toBe(true);
    expect(res.body.data.id).toBeDefined();
  });

  it("API Key가 누락되거나 위조된 경우 401/403으로 즉각 차단해야 한다", async () => {
    const res = await request(app)
      .post("/api/v1/documents")
      .set("X-API-Key", "lm_live_fake_attacker_key")
      .send({ title: "Hack" });

    expect(res.status).toBe(403);
    expect(res.body.error.code).toBe("FORBIDDEN_INVALID_KEY");
  });
});
```
