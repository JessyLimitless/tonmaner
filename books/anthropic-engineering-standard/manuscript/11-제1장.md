## '프롬프트 만능주의'의 붕괴: 컨텍스트 오염(Context Drift)과 스파게티 코드의 필연성

터미널이나 웹 인터페이스에서 LLM에게 코딩을 지시하는 첫 10분은 경이롭습니다. "간단한 할 일 관리 앱을 React와 Tailwind CSS로 만들어줘"라는 한 줄의 프롬프트만으로도, 스타일링이 완벽하게 적용된 단일 파일 컴포넌트가 눈앞에 나타납니다. 우리는 이 단계에서 흔히 엄청난 착각을 마주합니다. 자연어 프롬프트만 잘 다듬으면 복잡한 프로덕션 소프트웨어도 쉽게 완성할 수 있을 것이라는 착각, 바로 [프롬프트 만능주의(Prompt Omnipotence)]{.dot}입니다.

그러나 프로젝트가 단순 토이 프로젝트를 넘어 실제 서비스의 형태를 갖추기 시작하면, 이 마법 같은 생산성은 급격히 시스템 붕괴의 전조로 뒤바뀝니다.

### '대화형 코딩'이 필연적으로 실패하는 메커니즘

대부분의 개발자가 AI 코딩 도구를 처음 접할 때 사용하는 방식은 '즉흥적 질의응답(Chat-and-Fix)'입니다.

::: {.scene}
[즉흥적 질의응답 — Chat-and-Fix]{.label}

1. "A 기능을 만들어줘."
2. 코드가 출력되면 프로젝트에 복사·붙여넣기한다.
3. 실행해보니 에러가 발생한다. "이런 에러가 나는데 고쳐줘."
4. AI가 코드를 고쳐준다.
5. "이제 B 기능도 추가해줘."
:::

이 패턴을 대여섯 번만 반복하면 코드베이스는 급속도로 오염되기 시작합니다. AI 모델이 이전 대화에서 자신이 세웠던 상태 관리 규칙을 스스로 위반하고, 방금 전 작성한 유틸리티 함수의 이름을 잊어버린 채 새로운 함수를 중복 선언하며, 컴포넌트 간의 책임과 경계를 무너뜨립니다.

이 현상이 발생하는 근본적인 이유는 개발자의 코딩 역량이나 AI의 파라미터 부족 때문이 아닙니다. **대화(Chat)라는 매체 자체가 지닌 구조적 결함** 때문입니다.

### 컨텍스트 오염(Context Drift)의 해부

거대언어모델은 이전의 모든 대화 기록을 프롬프트 입력창 뒤에 이어 붙이며 '다음에 올 가장 자연스러운 토큰'을 예측합니다. 대화형 인터페이스에서 우리가 주고받는 대화는 시간이 지날수록 다음과 같은 노이즈로 가득 차게 됩니다.

- "아, 방금 코드는 오타가 있었네요. 이렇게 수정하세요."
- "잠깐, 이 패키지 버전이 안 맞으니 다른 라이브러리로 바꿔보죠."
- 수백 줄에 달하는 터미널 스택 트레이스(Stack Trace) 에러 로그
- 일시적인 디버깅용 `console.log`와 임시 땜질 코드

이 모든 실패의 기록, 임시방편의 텍스트, 모순된 지시사항들이 고스란히 컨텍스트 윈도우(Context Window)에 누적됩니다.

<!--figure: context-drift | 대화가 쌓일수록 사용자 의도가 차지하는 비중은 줄고, 그 자리를 실패의 기록이 채운다.-->

이것이 바로 [컨텍스트 오염(Context Drift)]{.dot}입니다. 모델의 어텐션 메커니즘(Attention Mechanism)은 잡음으로 가득 찬 수만 개의 토큰 사이에서 방황하며, 시스템의 진정한 목표가 무엇인지 잊어버립니다. 결국 AI는 직전 턴의 에러를 덮기 위해 또 다른 임시 코드를 짜내는 '악순환의 땜질 루프'에 갇히게 됩니다.

### 통제되지 않은 엔트로피: AI가 양산하는 스파게티 코드

사람 개발자가 작성하는 스파게티 코드는 대개 게으름이나 설계 미숙에서 비롯됩니다. 반면, 프롬프트 만능주의에 빠진 AI가 양산하는 스파게티 코드는 '초고속 확률적 과잉 생산'에서 비롯됩니다.

- **인터페이스 파괴**: 백엔드 API의 응답 규격(JSON 필드명)을 임의로 변경하여 프론트엔드의 렌더링을 깨뜨립니다.
- **무상태성(Statelessness)의 역설**: AI는 프로젝트 전체의 디렉토리 구조를 '암묵지'로 알고 있지 못합니다. 매 프롬프트마다 가장 확률이 높은 단일 파일 해법을 제안하므로, 기존 모듈을 재사용하지 않고 똑같은 로직을 파일마다 새로 선언합니다.
- **기술 부채의 압축 폭발**: 사람이 몇 주에 걸쳐 서서히 쌓을 기술 부채를, AI는 단 [30분]{.figure-hl} 만에 수천 줄 단위로 생성해 냅니다.

많은 개발자들이 "AI로 코딩하려다가 디버깅하느라 하루를 다 날렸다"며 손을 터는 지점이 바로 여기입니다.

### 문제는 프롬프트가 아니라 '기준점(Grounding)'의 부재다

프롬프트 엔지니어링의 미세한 문구 수정(예: "너는 최고의 시니어 개발자야", "숨을 깊게 들이쉬고 단계적으로 생각해")은 이러한 구조적 붕괴를 결코 막지 못합니다.

건축 현장에 비유하자면, 설계도면 한 장 없이 인부들에게 구두로 "여기 벽돌 좀 쌓아봐", "어? 거기가 아닌가 보네, 다시 허물고 저쪽에 기둥 세워봐"라고 끊임없이 지시하는 것과 같습니다. 아무리 손이 빠른 인부(AI)를 고용했더라도 도면이 없다면 건물은 3층을 채 올리지 못하고 무너집니다.

AI 에이전트가 흔들리지 않고 수천 줄의 코드를 작성하도록 만들려면, 대화창이라는 휘발성 공간을 벗어나야 합니다. 시스템의 제약, 데이터의 형태, 아키텍처의 경계선이 명시된 **변하지 않는 기준점(Ground Truth)** 을 코드베이스 안에 고정해야 합니다.

앤스로픽이 모델 자체를 제어할 때 사용했던 원리, 즉 헌법적 명세(Constitutional Specification)가 소프트웨어 엔지니어링에 도입되어야 하는 이유가 바로 여기에 있습니다.


## 헌법적 AI(Constitutional AI) 원리의 엔지니어링 적용: 시스템 제약과 규칙의 텍스트 선언

대화형 프롬프트가 필연적으로 컨텍스트 오염을 낳는다면, 모델의 출력을 흔들림 없이 통제할 대안은 무엇인가?

해답의 실마리는 앤스로픽이 거대언어모델 클로드(Claude)를 훈련할 때 고안한 정렬(Alignment) 기법, 바로 **헌법적 AI(Constitutional AI, CAI)** 에 있습니다.

### 헌법적 AI(Constitutional AI)의 태동: 인간 피드백의 한계

초기 생성형 AI의 안전성과 동작을 제어하던 표준 방식은 인간 피드백 기반 강화학습(RLHF, Reinforcement Learning from Human Feedback)이었습니다. 수많은 레이블러(사람)가 모델의 출력을 일일이 읽고 "이 답변은 유해하다", "이 답변은 도움이 된다"며 점수를 매겼습니다.

그러나 이 방식은 두 가지 치명적인 결함을 안고 있었습니다.

- **일관성의 붕괴**: 수천 명의 작업자가 각자 다른 기준과 편향으로 평가하므로, 모델에게 전달되는 보상 신호가 일관되지 않고 충돌했습니다.
- **확장성(Scalability)의 병목**: 시스템이 복잡해질수록 사람이 수작업으로 모든 코너 케이스를 검수하고 교정하는 것은 불가능에 가까웠습니다.

앤스로픽은 이 난제를 풀기 위해 발상을 완전히 전환했습니다. 수많은 사람의 주관적 평가 대신, 시스템 전체가 준수해야 할 명문화된 원칙의 목록, 즉 '헌법(Constitution)'을 텍스트로 정의하고, 모델 스스로가 이 헌법에 비추어 자신의 출력을 비판(Critique)하고 교정(Revision)하도록 만든 것입니다.

<!--figure: cai-loop | 원칙을 텍스트로 박아두면 교정은 사람의 감시가 아니라 모델 내부의 루프에서 일어난다.-->

원칙을 텍스트로 명문화하자 모델의 동작은 예측 가능해졌고, 사람이 일일이 감시하지 않아도 시스템은 스스로 정렬을 유지했습니다.

### AI 코딩 엔지니어링으로의 전이: 코드가 아닌 '헌법'을 먼저 세워라

이 원리는 에이전트를 활용한 소프트웨어 엔지니어링에도 1:1로 정확히 치환됩니다.

개발자가 대화창에서 AI와 승강이를 벌이는 이유는, 매 순간 사람이 즉흥적으로 'RLHF 작업자' 역할을 수행하고 있기 때문입니다. "이건 이렇게 짜지 마", "이 라이브러리 쓰지 마", "타입 에러 났잖아"라며 파편화된 피드백을 실시간으로 던지는 방식은 모델을 혼란에 빠뜨릴 뿐입니다.

소프트웨어 개발에서 헌법(Constitution)이란 곧 **시스템 제약 조건과 아키텍처 규칙의 텍스트 선언**입니다.

::: {.formula}
[네거티브 제약 — 하지 말아야 할 것]{.label}

- ORM을 임의로 도입하지 말고 순수 SQL 쿼리 빌더만 사용할 것.
- 컴포넌트 내부에 비즈니스 로직을 직접 작성하지 말고, 항상 커스텀 훅으로 분리할 것.
- 전역 상태 관리 라이브러리(Redux, Zustand 등)를 추가하지 말고 Context API로만 처리할 것.
:::

::: {.formula}
[포지티브 규칙 — 반드시 지켜야 할 것]{.label}

- 모든 API 응답은 사전에 정의된 `ApiResponse<T>` 제네릭 인터페이스 규격을 준수할 것.
- 데이터베이스 변경 작업은 반드시 멱등성(Idempotency)을 보장하는 트랜잭션으로 감쌀 것.
- 에러 발생 시 사용자 친화적인 메시지와 내부 추적용 에러 코드를 함께 반환할 것.
:::

이러한 규칙들을 개발자의 머릿속에 '암묵지'로 남겨둔 채 코드를 짜라고 지시하면, AI는 확률적으로 가장 흔한 인터넷 예제 코드를 긁어모아 제멋대로 조합합니다. 반면, 프로젝트 루트에 마크다운 문서 형태로 이 '헌법'을 단단히 고정해 두면 개발 환경은 완전히 달라집니다.

### 텍스트 명세가 시스템의 컴파일러가 되는 순간

전통적인 컴파일러(GCC, Rustc, TypeScript 등)는 문법적 오류와 타입 불일치를 기계적으로 검사합니다. 그러나 "이 컴포넌트가 우리 팀의 디렉토리 설계 철학에 부합하는가?", "이 API 호출이 시스템의 캐싱 정책을 따르고 있는가?"와 같은 아키텍처 레벨의 정합성은 컴파일러가 잡아내지 못합니다.

명문화된 헌법적 명세(Constitutional Spec)는 거대언어모델을 [아키텍처 레벨의 지능형 컴파일러]{.dot}로 만듭니다.

AI 에이전트에게 코드를 생성하게 할 때, 이 헌법 명세를 시스템 프롬프트나 루트 컨텍스트로 주입하면 에이전트는 코드를 출력하기 직전에 자체적인 검증 루프를 돕니다.

::: {.scene}
[에이전트의 자체 검증 루프]{.label}

"잠깐, 방금 작성한 코드에서 `fetch`를 직접 호출하고 있군. 명세서 제4조에 따르면 모든 네트워크 요청은 `ApiClient` 싱글톤 인스턴스를 거쳐야 한다. 코드를 교정해서 출력하자."
:::

개발자가 지적하기 전에 AI가 명세를 바탕으로 스스로 **자가 교정(Self-Correction)** 을 수행하는 것입니다. 이것이 바로 앤스로픽이 모델을 통제했던 방식이자, 우리가 복잡한 소프트웨어를 AI 네이티브 방식으로 구축할 때 반드시 도입해야 할 첫 번째 엔지니어링 표준입니다.

### 자연어 코딩의 핵심은 '자연어'가 아니라 '규칙'이다

'자연어로 코딩한다'는 말은 아무렇게나 말해도 컴퓨터가 찰떡같이 알아듣는다는 뜻이 아닙니다. 모호하기 짝이 없는 자연어를 논리적 모순이 없는 엄격한 법률 문서(Constitution)의 수준으로 끌어올려 선언할 수 있을 때, 비로소 자연어는 가장 강력한 프로그래밍 언어가 됩니다.

::: {.callout}
코드를 한 줄도 작성하지 않은 상태에서 시스템의 제약과 원칙을 텍스트로 완벽하게 선언하는 작업. 이것이 바로 **명세 주도 개발(Spec-Driven Development)** 의 첫걸음입니다.
:::


## 단일 진실 공급원(SSOT): 코드가 아닌 마크다운 명세가 시스템 원본이 되는 체계

전통적인 소프트웨어 공학에서 절대적인 진실은 언제나 '동작하는 코드(Working Code)'였습니다.

문서와 주석은 작성되는 순간부터 낡기 시작하며, 기획서나 아키텍처 다이어그램은 릴리스 주기를 몇 번 거치면 실제 코드베이스와 괴리되어 무용지물이 되기 일쑤였습니다. 익스트림 프로그래밍(XP)과 애자일 선언문이 "포괄적인 문서보다 동작하는 소프트웨어"를 앞세웠던 까닭도, 코드만이 시스템의 실제 상태를 대변하는 유일한 진실 공급원(Single Source of Truth, SSOT)이었기 때문입니다.

그러나 거대언어모델(LLM)이 코드를 생성하고 리팩토링하는 AI 네이티브 환경에 들어서면서, 이 오랜 상식은 정반대로 뒤집힙니다.

### '코드가 진실'일 때 AI 개발이 붕괴하는 과정

AI 에이전트에게 이미 작성된 수천~수만 줄의 소스코드를 단일 진실 공급원으로 제시하면 어떤 일이 벌어질까요?

- **컨텍스트 윈도우 과부하 및 토큰 낭비**: 전체 저장소의 소스코드를 매번 모델의 컨텍스트에 쏟아부을 수 없습니다. 프롬프트 캐싱이나 최신 모델의 대용량 컨텍스트 창을 활용하더라도, 수만 줄의 문법적 구문(Syntax boilerplate), 임포트 문, 닫는 괄호, 타입 정의 등이 어텐션 메커니즘의 집중도를 급격히 떨어뜨립니다.
- **의도(Intent)의 실종**: 코드는 '어떻게(How)' 동작하는지만을 보여줄 뿐, 시스템이 '왜(Why)' 그렇게 동작해야 하는지, 즉 원래의 비즈니스 목적과 불변의 제약 조건을 담지 못합니다. AI는 코드의 특정 구현을 우연한 디테일인지 핵심 규칙인지 구분하지 못하고, 요구사항을 처리하는 과정에서 필수적인 아키텍처 의도를 훼손해 버립니다.
- **오류의 증폭과 오염 전파**: 기존 코드에 미세한 버그나 레거시 패턴이 섞여 있다면, AI는 이를 '모범 답안'으로 학습하고 복제합니다. 코드가 진실인 시스템에서는 에러가 새로운 에러를 낳으며 코드베이스 전체를 오염시킵니다.

AI 시대에 소스코드는 더 이상 시스템의 최상위 원본이 될 수 없습니다. 코드는 명세로부터 파생된 [부산물(Artifact)]{.dot}에 불과합니다.

### 마크다운(Markdown): 인간과 기계를 잇는 완벽한 명세 포맷

진정한 단일 진실 공급원의 역할을 수행하려면 인간 엔지니어에게는 읽고 쓰기 쉬운 자연스러운 언어여야 하고, AI 에이전트에게는 구조화된 데이터로 즉시 파싱될 수 있어야 합니다. 이 접점에 존재하는 형식이 바로 마크다운(Markdown)입니다.

마크다운은 단순한 서식 도구가 아닙니다. 다음과 같은 엔지니어링적 장점을 지닌 표준 명세 포맷입니다.

- **Git을 통한 완전한 버전 관리**: 바이너리 문서(워드, 노션 등)와 달리 소스코드 리포지토리 내부에서 브랜치, 커밋, PR, 코드 리뷰 흐름을 코드와 완벽히 동일하게 공유합니다. 명세의 변경 이력이 곧 아키텍처의 변경 이력이 됩니다.
- **초고밀도 정보량과 토큰 최적화**: HTML이나 JSON에 비해 불필요한 태그와 메타데이터가 극도로 적습니다. 헤딩(`#`, `##`), 목록(`-`, `1.`), 표(`|`), 코드 블록 등 최소한의 기호만으로 시스템의 계층 구조를 명확히 표현하므로, LLM의 토큰 소비를 최소화하면서 논리적 위계를 가장 정확히 전달합니다.
- **파싱 자동화와의 친화성**: 규격화된 마크다운 테이블과 코드 블록은 스크립트나 MCP 도구를 통해 DDL 쿼리, 타입 선언 파일, 라우팅 테이블로 즉시 자동 추출될 수 있습니다.

### 명세(Spec)가 시스템의 원본이 되는 역전된 워크플로우

명세를 단일 진실 공급원으로 확립한 개발 환경에서는 작업의 흐름이 근본적으로 바뀝니다.

<!--figure: ssot-flow | 코드는 더 이상 원본이 아니다. 명세가 원본이고, 코드는 에이전트가 그것을 컴파일한 결과다.-->

시스템을 변경해야 할 때, 엔지니어는 절대 에디터나 대화창에서 소스코드를 직접 만지지 않습니다.

1. **명세 수정**: 새로운 기능 요구사항, 바뀐 DB 필드, 새로운 UI 컴포넌트의 규칙을 리포지토리 루트의 마크다운 명세 문서(`PRD.md`, `ARCHITECTURE.md`, `DATA_SCHEMA.md`, `UI_SPEC.md`)에 반영합니다.
2. **정렬 검증**: 수정된 명세가 기존의 다른 3대 명세와 충돌하지 않는지 교차 검토합니다.
3. **에이전트 컴파일 지시**: AI 에이전트에게 명세의 변경 사항을 읽게 하고, "변경된 `03_DATA_SCHEMA.md`에 맞추어 백엔드 모델과 마이그레이션 코드를 업데이트하라"고 선언합니다.

이 구조에서 버그가 발생하거나 코드가 잘못 생성되었다면, 그것은 코드를 디버깅할 문제가 아니라 **명세서의 제약 조건이 느슨했음**을 의미합니다. 코드를 뜯어고치는 대신 명세 문서의 규칙을 단단히 조이고 다시 에이전트를 컴파일하면, 시스템 전체가 다시 정렬됩니다.

### 리포지토리 루트에 존재하는 영구적 진실: SPEC.md와 CLAUDE.md

대화창의 세션이 종료되면 AI의 단기 기억은 증발합니다. 그러나 프로젝트 루트 디렉토리에 자리 잡은 마크다운 명세 파일들과 컨텍스트 지침 파일(`CLAUDE.md`)은 영구적으로 살아남습니다.

새로운 작업을 시작할 때마다 에이전트는 리포지토리의 마크다운 명세를 읽고 첫 1초 만에 프로젝트의 전체 맥락을 [100%]{.figure-hl} 복원합니다.

주니어 개발자가 팀에 새로 합류하든, 최신 고성능 모델로 LLM을 교체하든, 단일 진실 공급원인 마크다운 명세가 견고하게 유지되는 한 시스템의 아키텍처는 결코 흔들리지 않습니다.

::: {.callout}
코드가 아닌 명세를 진실로 삼는 순간, 개발자는 비로소 끝없는 디버깅의 수렁에서 벗어나 전체 시스템의 구조와 방향을 조망하는 진정한 **아키텍트**로 거듭나게 됩니다.
:::
