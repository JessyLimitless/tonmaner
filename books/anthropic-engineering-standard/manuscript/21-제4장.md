## 01_PRD.md: 문제 정의, 핵심 가치 제안(UVP), 단계별 스코프 통제 템플릿

전통적인 소프트웨어 개발 환경에서 제품 요구사항 정의서(PRD, Product Requirements Document)는 기획자나 PM이 비즈니스 요구를 서술하는 수십 페이지짜리 워드 문서였습니다. 이 문서는 프로젝트가 시작될 때 한 번 읽히고 나면, 개발이 진행될수록 서랍 속에 방치되어 실제 코드와 완전히 괴리되곤 했습니다.

그러나 AI 네이티브 엔지니어링 환경에서 `01_PRD.md`는 단순한 기획서가 아닙니다. 에이전트의 모든 아키텍처적 판단을 지배하는 [최상위 나침반이자 시스템의 헌법 제1조]{.dot}입니다.

AI 에이전트는 코드를 생성하다가 두 가지 구현 방식을 두고 선택의 기로에 섰을 때, 반드시 PRD에 명시된 '비즈니스 목적'을 기준으로 의사결정을 내립니다. 따라서 `01_PRD.md`는 기획자를 위한 산문이 아니라, 기계(AI)가 파싱하고 이해할 수 있는 엄밀한 논리 구조로 작성되어야 합니다.

### 문제 정의와 핵심 가치 제안(UVP): AI의 섀도우 엔지니어링 방지

::: {.scene}
[한 줄짜리 지시]{.label}

"마크다운 기반의 지식 아카이브 시스템을 만들어라."
:::

만약 이 한 줄만 던져준다면 AI는 어떤 코드를 생성할까요? 어떤 에이전트는 무거운 엔터프라이즈급 CMS(Content Management System)와 복잡한 권한 인가 시스템을 붙일 것이고, 어떤 에이전트는 노션(Notion)처럼 화려한 블록 에디터를 만들려고 시도할 것입니다. 이것이 AI가 임의로 아키텍처를 결정해버리는 [섀도우 엔지니어링(Shadow Engineering)]{.dot} 현상입니다.

이를 막으려면 문제 정의(Problem)와 핵심 가치 제안(UVP, Unique Value Proposition)을 명확히 텍스트로 선언해야 합니다.

::: {.formula}
[문제 정의와 UVP 선언 예시]{.label}

- **문제 정의** — "기존 지식 관리 툴은 무겁고 외부 클라우드에 종속되어 있어, 로컬에서 빠르게 마크다운 파일을 검색하고 관리하기 어렵다."
- **핵심 가치 제안(UVP)** — "클라우드 종속성 없는 완전한 로컬 퍼스트(Local-first). 군더더기 없는 초고속 파싱과 키보드 중심의 2-Pane 마크다운 인터랙티브 뷰어."
:::

이 UVP가 주입되는 순간, 에이전트는 "아, 이 서비스는 무거운 외부 라이브러리나 화려한 에디터 기능보다 파싱 속도와 로컬 파일 시스템 제어가 최우선이구나"라고 맥락을 파악하고 그에 맞는 경량화된 아키텍처와 라이브러리를 스스로 채택하게 됩니다.

### 안티 골(Non-Goals): 에이전트의 과잉 생산 통제

AI는 본능적으로 '더 많이, 더 그럴듯하게' 코드를 짜려는 과잉 생산(Over-engineering)의 경향을 가집니다. 따라서 해야 할 일을 나열하는 것만큼이나 [절대 하지 말아야 할 일(Non-Goals 또는 Out of Scope)]{.dot}을 명시하는 것이 치명적으로 중요합니다.

네거티브 제약(Negative Constraints)이 선언되지 않으면, 에이전트는 당신이 묻지도 않은 로그인 세션 관리, 비밀번호 찾기 로직, 다국어 처리(i18n) 모듈을 멋대로 생성하여 시스템의 복잡도를 높입니다.

::: {.formula}
[Non-Goals 예시]{.label}

- "이 서비스는 다중 사용자(Multi-user) 권한 관리를 지원하지 않는다 (단일 관리자 계정만 존재)."
- "웹에서 직접 문서를 수정하는 WYSIWYG 에디터 기능은 구현하지 않는다 (읽기 전용 뷰어에 집중)."
- "결제 연동이나 다국어 지원은 고려하지 않는다."
:::

안티 골을 선언하는 순간, AI의 컨텍스트 윈도우 안에서 수많은 불필요한 라이브러리 참조와 환각의 가능성이 즉시 소멸합니다.

### 단계별 스코프 제어(Phase-Driven Scope)

앞 장에서 강조한 바와 같이, PRD는 빅뱅 방식의 구현을 막기 위해 모든 기능을 [Phase 1], [Phase 2], [Phase 3] 태그로 엄격하게 수평 분할해야 합니다.

각 단계는 독립적으로 실행 가능(Executable)해야 하며, 다음 단계의 개발이 지연되더라도 그 자체로 온전한 소프트웨어로 동작해야 합니다.

### 실전 템플릿: 01_PRD.md 표준 규격

아래는 앤스로픽식 명세 주도 개발에 최적화된 `01_PRD.md`의 실제 마크다운 템플릿입니다. 이 템플릿은 우리 책의 실습 프로젝트인 〈마크다운 지식 아카이브 SaaS〉에 맞추어 작성되었습니다. 프로젝트를 시작할 때 이 구조를 리포지토리 루트의 `docs/specs/01_PRD.md`로 저장하십시오.

```markdown
# 01_PRD: Markdown Knowledge Archive SaaS

## 1. Meta Information
* **Project Name**: LinkMD (가칭)
* **Status**: Draft -> [Approved]
* **Target Audience**: 마크다운으로 지식을 정리하는 1인 개발자, 리서처, 테크니컬 라이터

## 2. Product Vision
### 2.1 Problem Definition
개발자와 리서처들은 수많은 마크다운 파일과 웹 스크랩 자료를 로컬에 쌓아두지만,
이를 유기적으로 연결하고 즉각적으로 검색하며 필요 시 외부에 정적 웹으로 공유하는
가볍고 통합된 파이프라인이 부재하다.

### 2.2 Unique Value Proposition (UVP)
1. **Local-First Speed**: DB나 서버 세팅 없이 로컬 폴더의 마크다운을 즉시 렌더링.
2. **Seamless Web Scraping**: 클릭 한 번으로 웹 아티클을 순수 마크다운으로 변환하여 아카이빙.
3. **One-Click Share**: 내 로컬 지식창고를 클라우드나 정적 API를 통해 쉽게 외부에 공유.

## 3. Non-Goals (절대 구현하지 말 것)
* WYSIWYG 블록 기반 에디터 (노션 스타일) 도입 금지. 오직 순수 마크다운 텍스트 렌더링에 집중.
* 다중 사용자 간의 실시간 동시 편집(CRDT) 기능 미지원.
* 복잡한 RBAC(Role-Based Access Control) 권한 시스템 제외.
  (소유자 vs 익명 읽기 권한으로 이분화)

## 4. Phase-Driven Scope
에이전트는 코드 생성 시 현재 지시받은 Phase의 요구사항만 구현하며,
상위 Phase의 기능은 무시할 것.

### [Phase 1] MVP Core Engine & 2-Pane Viewer
* **목표**: 로컬 환경에서 마크다운 파싱 및 인터랙티브 뷰어 확인.
* **핵심 기능**:
  - 로컬 디렉토리의 `.md` 파일을 읽어 트리 구조로 시각화 (Sidebar).
  - 마크다운 파일을 HTML로 변환하여 렌더링하는 Main Pane.
  - 마크다운 프론트매터(Frontmatter) 기반의 태그(Tags) 추출 및 필터링.

### [Phase 2] Full-Stack Database & Web Scraper (MCP)
* **목표**: 영속성 데이터 저장 및 외부 데이터 수집.
* **핵심 기능**:
  - 로컬 파일을 관계형 DB(PostgreSQL/SQLite)로 마이그레이션.
  - 본문 Full-Text 검색 (Search Bar).
  - MCP(Puppeteer/Fetch) 연동을 통한 외부 URL의 본문 마크다운 추출 및 자동 저장.

### [Phase 3] Cloud Deployment & B2B API Portal
* **목표**: 상용 서비스 배포 및 외부 확장성 확보.
* **핵심 기능**:
  - Docker 컨테이너 기반 풀스택 배포.
  - 특정 문서/디렉토리에 대한 Public Share URL(읽기 전용) 생성.
  - 서드파티 앱(예: Raycast, Obsidian)에서 접근 가능한 읽기 전용 REST API 개방.
```

## 02_ARCHITECTURE.md: 풀스택 데이터 흐름과 상태 머신(State Machine) 설계

기획 명세(`01_PRD.md`)가 시스템이 달성해야 할 목적(Why)과 비즈니스 경계선을 선언했다면, `02_ARCHITECTURE.md`는 이를 현실의 소프트웨어로 구현하기 위한 물리적 데이터 파이프라인(Data Flow)과 상태 전이 규칙(State Machine)을 정의하는 기술적 설계도입니다.

AI 에이전트에게 아키텍처 문서 없이 코드 생성을 지시하면 어떤 일이 벌어질까요? 프론트엔드 컴포넌트 내부에서 직접 외부 API를 호출해 상태를 꼬이게 만들거나, 파일 I/O 작업을 메인 스레드에서 블로킹 형태로 처리하고, 비동기 데이터 통신 중에 중복 요청을 난사하는 등 구조적 결함을 드러냅니다.

에이전트는 '동작하는 코드'는 짤 수 있어도, '데이터가 어느 계층을 통해 흘러야 하는지'에 대한 거시적 질서는 스스로 세우지 못합니다. 이 질서를 마크다운으로 강제하는 문서가 바로 `02_ARCHITECTURE.md`입니다.

### 데이터 흐름의 단방향성(Unidirectional Data Flow) 선언

AI 에이전트가 복잡한 풀스택 애플리케이션을 코딩할 때 가장 흔하게 저지르는 실수는 컴포넌트 간, 계층 간의 양방향 참조와 결합도(Coupling) 상승입니다.

`02_ARCHITECTURE.md`에서는 데이터의 유입부터 저장, 화면 렌더링에 이르는 경로를 [단방향 파이프라인]{.dot}으로 못 박아야 합니다.

::: {.formula}
[단방향 3계층]{.label}

1. **수집 및 파싱 계층(Ingestion Layer)** — 로컬 파일 시스템의 `.md` 파일 또는 MCP(Fetch/Puppeteer)를 통해 유입된 원시 데이터(Raw Data)를 검증하고 AST(Abstract Syntax Tree)로 정규화.
2. **서비스 및 영속성 계층(Service & Persistence Layer)** — 비즈니스 룰 검증, 관계형 DB 저장, 전문 검색(Full-Text) 색인 토큰 추출.
3. **표현 계층(Presentation Layer)** — 서버로부터 정제된 상태(State)만을 단방향으로 수신하여 읽기 전용 뷰어에 렌더링. 화면의 액션은 오직 정의된 이벤트 디스패처를 통해서만 하위 계층으로 전달.
:::

이 계층 분리가 명세서에 텍스트로 명시되어 있으면, AI 에이전트는 프론트엔드 UI 파일 안에 파일 읽기 로직이나 DB 쿼리를 직접 작성하는 식의 아키텍처 오염을 일으키지 않습니다.

### 모호성을 박멸하는 상태 머신(State Machine) 설계

비동기 네트워크 통신이나 파일 파싱 과정에서 발생하는 버그의 상당수는 '정의되지 않은 중간 상태(Undefined Intermediate State)'에서 발생합니다.

예를 들어 웹 아티클을 스크랩하여 마크다운으로 변환하는 작업을 에이전트에게 맡기면, 에이전트는 흔히 다음과 같은 불완전한 boolean 플래그를 만듭니다.

```typescript
// 안티 패턴: 모호한 boolean 상태 조합 (2^3 = 8가지 비정상 상태 유발)
const [isLoading, setIsLoading] = useState(false);
const [isError, setIsError] = useState(false);
const [isSuccess, setIsSuccess] = useState(false);
```

이런 코드는 네트워크 지연이 발생하거나 사용자가 연속으로 버튼을 누르면 `isLoading === true`이면서 동시에 `isError === true`가 되는 기괴한 상태에 빠집니다.

이를 방지하기 위해 `02_ARCHITECTURE.md`는 시스템의 모든 핵심 비즈니스 흐름을 유한 상태 머신(FSM, Finite State Machine)으로 규정해야 합니다.

<!--figure: fsm-ingestion | 상태를 열거하면 조합이 사라진다. 로딩이면서 동시에 에러인 상태는 애초에 존재할 수 없게 된다.-->

전이표는 명세서 안에만 두지 말고 본문에서도 한 번 펼쳐 봅니다. 이 표가 곧 구현 계약입니다.

::: {.table-wrap}
| 현재 상태 | 이벤트 | 다음 상태 | 부수 효과 |
|---|---|---|---|
| `IDLE` | `START_JOB` | `FETCHING` | 타임아웃 타이머 시작 |
| `FETCHING` | `FETCH_SUCCESS` | `PARSING` | HTML 문자열 메모리 로드 |
| `FETCHING` | `FETCH_FAIL` | `ERROR_ABORT` | 네트워크 에러 로그 기록, 롤백 |
| `PARSING` | `PARSE_SUCCESS` | `PERSISTING` | 본문·메타데이터 추출 완료 |
| `PARSING` | `PARSE_FAIL` | `ERROR_ABORT` | 파싱 실패 사유 클라이언트 전달 |
| `PERSISTING` | `PERSIST_SUCCESS` | `READY` | DB 커밋, 뷰어 갱신 이벤트 발송 |
| `PERSISTING` | `PERSIST_FAIL` | `ERROR_ABORT` | DB 트랜잭션 롤백 |
| `ERROR_ABORT` | `RESET` | `IDLE` | 에러 리포트 초기화 |
:::

표에 없는 칸은 **금지된 전이**입니다. `FETCHING`에서 곧바로 `READY`로 가는 길은 없습니다. 이 빈칸들이 boolean 플래그 조합이 만들어내던 기괴한 상태를 통째로 지웁니다.

가능한 상태의 집합(State Set)과 상태를 전이시키는 허용된 전이 조건(Allowed Transitions)을 명세서에 표와 다이어그램으로 명시하면, 에이전트는 불완전한 boolean 변수를 남발하지 않고 완전한 열거형 타입(Enum 또는 Union Type)과 상태 전이 리듀서(Reducer)를 정확하게 구현합니다.

아래는 〈마크다운 지식 아카이브 SaaS〉의 데이터 파이프라인과 상태 머신을 정의한 `02_ARCHITECTURE.md`의 실제 명세 템플릿입니다. 프로젝트 루트의 `docs/specs/02_ARCHITECTURE.md`에 배치합니다.

````markdown
# 02_ARCHITECTURE: System Design & State Pipeline

## 1. System Topology & Layers
시스템은 엄격한 3계층 단방향 아키텍처를 준수하며,
상위 계층은 하위 계층의 내부 구현을 직접 참조하지 않는다.

```text
[Client Layer]     React 2-Pane Viewer (State Observer & Action Dispatcher)
                         │ ▲  (HTTP REST / Server-Sent Events)
                         ▼ │
[Core Server]      FastAPI / Express Gateway (Validation, Auth, FSM Engine)
                         │ ▲
                         ▼ │
[Resource Layer]   File System (.md AST) ── PostgreSQL (Storage) ── MCP Agent
```

### [Phase 1] Local Architecture
* **데이터 소스**: 로컬 디렉토리 파일 시스템 (`./vault`).
* **파싱 파이프라인**:
  - `fs.watch` 기반 파일 변경 감지.
  - Frontmatter 메타데이터 분리 (YAML Parser).
  - Remark/Rehype 기반 마크다운 AST 변환.
  - 인메모리 색인 테이블 생성 (ID -> Document AST).
* **렌더링**: 로컬 번들 기반 2-Pane 레이아웃. 백엔드 DB 없음.

### [Phase 2] Full-Stack Data Pipeline
* **영속화 엔진**: Node.js/Express + PostgreSQL + Prisma ORM.
* **전문 검색 파이프라인**:
  - 마크다운 본문 파싱 시 텍스트 노드 추출 -> PostgreSQL tsvector 토큰화 트리거 실행.
* **MCP 어댑터 연동**:
  - Puppeteer MCP Server: 외부 웹페이지 DOM 캡처 -> Readability.js 마크다운 정제
    -> 영속화 큐 진입.

### [Phase 3] Production Cloud Topology
* **인프라**: Docker-Compose 기반 멀티 컨테이너 (Web, API, DB).
* **캐싱 및 읽기 전용 서빙**:
  - Public Share URL 요청 시 원본 DB 접근 전 In-Memory Cache(LRU) 검사.
* **API Gateway**:
  - Rate Limiter (토큰 버킷 알고리즘, 분당 60회 제한) 적용 후 내부 서비스 라우팅.

## 2. Ingestion Finite State Machine (FSM)
웹 수집 및 로컬 파일 인덱싱 파이프라인은 아래 명시된 상태(State) 외의
임의의 플래그를 조합하여 구현할 수 없다.

| Current State | Event           | Next State  | Action / Side Effect            |
|---------------|-----------------|-------------|---------------------------------|
| IDLE          | START_JOB       | FETCHING    | 타임아웃 타이머(10s) 시작        |
| FETCHING      | FETCH_SUCCESS   | PARSING     | HTML 문자열 메모리 로드          |
| FETCHING      | FETCH_FAIL      | ERROR_ABORT | 네트워크 에러 로그 기록, 롤백    |
| PARSING       | PARSE_SUCCESS   | PERSISTING  | 마크다운 본문·메타데이터 추출     |
| PARSING       | PARSE_FAIL      | ERROR_ABORT | AST 파싱 실패 사유 클라이언트 전달 |
| PERSISTING    | PERSIST_SUCCESS | READY       | DB 커밋, 뷰어 갱신 이벤트 발송    |
| PERSISTING    | PERSIST_FAIL    | ERROR_ABORT | DB 트랜잭션 롤백                 |
| ERROR_ABORT   | RESET           | IDLE        | 에러 리포트 초기화               |

## 3. Architecture Constraints (불변의 규칙)
* **No Direct DB Calls from UI**: 프론트엔드는 절대 DB 드라이버나
  로컬 파일 시스템 경로에 직접 접근할 수 없다.
* **Stateless Business Logic**: 모든 비즈니스 계산(단어 수 집계, 태그 추출, AST 생성)은
  외부 의존성이 없는 순수 함수(Pure Function)로 분리한다.
* **Graceful Degradation**: MCP 웹 수집기 실패 시에도 로컬 마크다운 뷰어 엔진은
  독립적으로 100% 정상 작동해야 한다.
````

### 요약: 길을 잃지 않는 지도를 쥐여주다

`02_ARCHITECTURE.md`가 마련되는 순간, AI 에이전트는 더 이상 인터넷에 널려 있는 무작위 블로그 코드를 흉내 내지 않습니다.

- 어떤 레이어에 코드를 배치해야 하는지,
- 상태 플래그를 어떻게 선언하고 전이시켜야 하는지,
- 외부 도구(MCP)가 실패했을 때 어떤 예외 경로로 복귀해야 하는지

::: {.callout}
그 모든 이동 경로가 명세서에 단단히 고정됩니다.

다음 절에서는 공공, 금융, 엔터프라이즈 환경에서 필수적으로 요구되는 폐쇄망, 온프레미스 sLLM, 망연계 아키텍처를 이 명세 체계 안에 어떻게 녹여내는지 살펴보겠습니다.
:::


## 엔터프라이즈 환경 대응: 공공·금융 폐쇄망, 온프레미스 sLLM 및 망연계 설계 포인트

일반적인 상용 SaaS 환경에서는 외부의 퍼블릭 LLM API(Anthropic Claude API, OpenAI API 등)를 호출하고, AWS나 Vercel과 같은 글로벌 퍼블릭 클라우드에 인프라를 배포하는 것이 자연스럽습니다. 그러나 엔터프라이즈, 특히 공공 기관, 국방, 금융, 의료와 같은 규제 산업(Regulated Industries)에 진입하는 순간, 개발 환경의 기본 전제는 완전히 뒤집힙니다.

::: {.formula}
[규제 산업이 뒤집는 세 가지 전제]{.label}

- 외부 인터넷 연결이 물리적 또는 논리적으로 완전 차단된 에어갭(Air-gapped) 폐쇄망.
- 개인정보, 비공개 금융 데이터, 국가 기밀 데이터의 외부 유출을 원천 금지하는 엄격한 데이터 주권(Data Sovereignty) 규제.
- 내부 인프라에 직접 호스팅해야 하는 온프레미스(On-Premises) 소형 거대언어모델(sLLM) 운용 제약.
:::

이러한 특수 환경에서 AI 네이티브 아키텍처를 구축할 때, 명세서(`02_ARCHITECTURE.md`)에 폐쇄망과 망연계 제약이 명문화되어 있지 않다면 AI 에이전트는 무용지물이 됩니다. 에이전트가 생성한 코드가 외부 CDN 스크립트를 참조하거나, 외부 API 엔드포인트를 하드코딩하여 빌드조차 되지 않는 치명적인 결함을 유발하기 때문입니다.

### 온프레미스 sLLM 서빙 엔진과 API 프록시 계층의 추상화

엔터프라이즈 폐쇄망 내부에서는 Claude Sonnet이나 Opus 같은 퍼블릭 클라우드 API를 직접 호출할 수 없습니다. 대신 사내 GPU 서버(H100, A100 클러스터 등)에 직접 구동되는 vLLM, Ollama, TGI(Text Generation Inference) 기반의 오픈소스 sLLM(Llama, Mistral, Qwen 파인튜닝 모델 등)을 활용해야 합니다.

이때 시스템 아키텍처는 [LLM 벤더 비종속적 인터페이스]{.dot}를 보장하도록 설계되어야 합니다.

<!--figure: llm-gateway | 벤더가 바뀌어도 코드는 바뀌지 않는다. 바뀌는 것은 게이트웨이 뒤편의 라우팅뿐이다.-->

`02_ARCHITECTURE.md`에 다음과 같은 원칙을 명시해야 합니다.

- **표준 프로토콜 인터페이스 규격화** — 모든 에이전트와 백엔드 서비스는 특정 클라우드 SDK를 직접 호출하지 않고, 내부 프록시 게이트웨이 엔드포인트(`http://internal-llm-gateway.local/v1`)만을 바라본다.
- **보안 등급별 모델 라우팅** — 데이터의 민감도 분류(Classification)에 따라, 비식별화된 공개 문서는 망연계 프록시를 통해 고성능 상위 모델로 분기하고, 민감 데이터는 사내 폐쇄망 sLLM으로만 라우팅하도록 강제한다.

### 망연계(Network DMZ) 솔루션과 파일 전송 아키텍처

공공 및 금융 시스템은 대개 업무망(내부망)과 인터넷망(외부망)이 분리되어 있습니다. 본 도서의 실전 프로젝트인 지식 아카이브 시스템이 외부 웹 아티클을 수집(MCP Scraper)하여 내부 아카이브로 들여오려면, 망연계 체계(연계 서버, 스토리지 스트리밍, 단방향 전송 장비)를 반드시 통과해야 합니다.

<!--figure: network-dmz | 외부에서 들어온 문서는 정제와 검증을 거쳐야만 업무망에 닿는다. 이 순서가 명세에 없으면 코드가 지름길을 만든다.-->

::: {.formula}
[망연계 수집 파이프라인]{.label}

1. **외부 인터넷망 수집 에이전트** — 외부망 DMZ 구간에 위치한 MCP Agent(Puppeteer/Fetch)가 지정된 웹 문서를 스크랩. 스크랩된 HTML에서 스크립트, 쿠키, 악성 코드를 제거하고 순수 텍스트 마크다운(Markdown)으로 정제.
2. **망연계 보안 검증 및 무결성 검사** — 정제된 마크다운 파일과 첨부 이미지를 사내 안티바이러스 엔진 및 악성 파일 탐지기(CDR)를 통해 전수 검사. 데이터 해시(SHA-256)를 생성하여 변조 여부 검증.
3. **내부 업무망 데이터 동기화** — 승인된 안전한 마크다운 파일만을 내부망 PostgreSQL 및 인덱서 엔진으로 스트리밍 주입.
:::

이 망분리 경계선과 파이프라인이 `02_ARCHITECTURE.md`에 선언되어 있어야, AI 에이전트가 "내부망 서버에서 외부 URL로 직접 `curl` 요청을 보내는" 구조적 보안 위반 코드를 짜지 않습니다.

### 에어갭(Air-gapped) 환경을 위한 의존성 및 패키지 제약 선언

폐쇄망 환경에서 가장 빈번하게 빌드가 터지는 원인은 '외부 CDN 및 패키지 저장소 의존성'입니다.

명세서의 네거티브 제약(Negative Constraints) 섹션에 다음 항목을 선언해야 합니다.

```markdown
### [Enterprise Security Constraints]
* **No External CDN**: 프론트엔드 HTML/React 코드에 `cdn.jsdelivr.net`,
  `cdnjs.cloudflare.com` 등의 외부 스크립트 링크 삽입 금지.
  모든 폰트, CSS, 아이콘은 프로젝트 번들 내부에 자체 호스팅(Self-hosted)할 것.
* **Private NPM / PyPI Registry**: 모든 의존성 패키지는 사내 사설 레지스트리
  (`nexus.internal.corp`)에서만 다운로드 가능하므로, 최신 실험적 라이브러리 사용을
  금지하고 장기 지원 버전(LTS)만 사용할 것.
* **Telemetry & Analytics Off**: 오픈소스 프레임워크나 라이브러리의 자체 원격 진단
  데이터 전송(Telemetry) 옵션을 소스코드 및 환경 변수 수준에서 명시적으로
  비활성화(`DO_NOT_TRACK=1`)할 것.
```

### 엔터프라이즈 환경 대응 명세가 가져오는 효과

아키텍처 문서에 이와 같은 엔터프라이즈 가드레일을 텍스트로 박아두면, 다음과 같은 결정적인 차이가 발생합니다.

- **인프라 감사 및 보안성 검토 통과** — 금융감독원, 공공기관 보안성 검토 시 "데이터가 외부로 나가지 않는다는 기술적 증거"를 명세서와 코드 아키텍처 수준에서 즉시 증명할 수 있습니다.
- **배포 실패 원인 하나의 제거** — 사내 폐쇄망 인프라에 도커 컨테이너를 올렸을 때 외부 연결 시도로 인해 컨테이너가 행(Hang)에 걸리거나 크래시되는 문제를 원천 차단합니다.
- **하이브리드 유연성** — 로컬 개발 시에는 개발용 경량 sLLM을 물리고, 클라우드 테스트 시에는 Claude API를, 상용 폐쇄망에서는 사내 vLLM 클러스터를 단 한 줄의 설정 변경만으로 오갈 수 있는 높은 이식성(Portability)을 확보하게 됩니다.

::: {.callout}
결국 엔터프라이즈 아키텍처의 성패는 복잡한 인프라 툴이 아니라, "시스템의 보안 경계선과 망연계 제약을 얼마나 엄격하게 텍스트 명세로 통제했는가"에 달려 있습니다.
:::
