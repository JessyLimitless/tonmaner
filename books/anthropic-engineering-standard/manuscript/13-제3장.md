# [03]{.ch-num} 점진적 단계별 빌드(Phase-Driven Iteration)


<!-- 여기부터 본문 -->


## 완벽주의의 함정: 왜 한 번에 거대한 시스템을 프롬프트로 생성하면 무너지는가?

인간 개발자가 범하기 쉬운 가장 매혹적이고 치명적인 유혹은 "완벽한 최종 형태를 단번에 만들어내려는 욕망"입니다.

명세 주도 개발(Spec-Driven Development)의 중요성을 이해한 엔지니어조차 초기에 동일한 실수를 저지릅니다. 수십 페이지에 달하는 기획 명세, 복잡한 ER 다이어그램, 수십 개의 API 엔드포인트, 화려한 디자인 시스템을 갖춘 UI 명세를 하나의 거대한 프롬프트에 담아 AI 에이전트에 던집니다.

::: {.scene}
[하나의 프롬프트에 전부]{.label}

"여기 완벽한 4대 명세서가 있어. 이 명세서를 바탕으로 회원가입, 권한 인가, 결제 모듈, 마크다운 에디터, 실시간 웹소켓 알림, 그리고 AWS 배포 인프라 스크립트까지 전부 한 번에 작성해 줘."
:::

이른바 [빅뱅(Big-Bang) 프롬프트]{.dot} 방식입니다.

엔지니어는 이 거대한 입력창 뒤에서 몇 분만 기다리면 상용 프로덕션 수준의 SaaS가 완성되어 튀어나올 것이라 기대합니다. 그러나 화면에 찍혀 나오는 결과물은 십중팔구 "그럴듯해 보이지만 실행하자마자 깨지는 거대한 코드 무더기"에 불과합니다.

### '빅뱅 생성'이 물리적으로 파멸하는 세 가지 이유

아무리 최신의 프론티어 LLM과 수십만 토큰의 거대한 컨텍스트 윈도우를 갖춘 모델이라 할지라도, '한 번에 거대한 시스템 구축하기'는 인공신경망의 계산 메커니즘상 실패할 수밖에 없습니다.

<!--figure: bigbang-collapse | 한 번에 전부 요구하면 실패는 세 갈래로 갈라진다. 주의력이 얇아지고, 분량을 줄이려 핵심 로직을 주석으로 건너뛰고, 그렇게 나온 코드는 원인을 추적할 수 없다.-->

**어텐션 희석(Attention Dilution)과 추론 대역폭의 한계**

LLM의 핵심 연산 메커니즘인 셀프 어텐션(Self-Attention)은 입력된 모든 토큰 간의 관계를 계산합니다. 한 번에 너무 많은 도메인(인증, 데이터베이스, 레이아웃, 결제, 상태 관리)을 동시에 요구하면, 모델의 '주의 집중력(Attention Resource)'은 얇고 넓게 분산됩니다. 그 결과, 개별 모듈에서는 반드시 지켜야 할 엄밀한 엣지 케이스 처리나 보안 검증 로직이 누락됩니다.

**출력 토큰 제한과 'TODO 스킵' 현상**

생성형 AI 모델에는 한 번의 요청에서 출력할 수 있는 물리적인 최대 토큰 한계(Max Output Tokens)가 존재합니다. 시스템 전체 코드를 한 번에 짜내려 하다 보면 이 용량 한계에 부딪히게 되고, 모델은 스스로 분량을 줄이기 위해 끔찍한 전략을 선택합니다.

```
// TODO: 실제 결제 승인 로직 구현 필요

// ... 기존 코드 유지 ...
```

핵심 비즈니스 로직을 주석 한 줄로 대충 건너뛰어 버리는 것입니다.

**디버깅 불가능성(Undebuggability)**

작동하지 않는 20줄짜리 함수를 고치는 것은 30초면 충분합니다. 하지만 서로 얽히고설킨 30개 파일, 3,000줄의 코드에서 발생하는 런타임 에러는 원인을 추적하는 것 자체가 악몽입니다. 어디서부터 잘못되었는지 파악하기 위해 에러 로그를 넣을 때마다 AI는 코드의 다른 부분을 멋대로 건드리며 혼란을 증폭시킵니다.

### 공개된 권고도 같은 곳을 가리킨다

<!-- ⚠ 인용 검증 필요 — 아래는 요지 서술이므로 블록 인용을 쓰지 않았다.
     《Building Effective Agents》 원문을 대조해 정확한 문장을 확보하면
     URL·접속일을 병기해 블록 인용으로 승격할 것. (감사 결과 A급 5번) -->

앤스로픽이 공개한 엔지니어링 문헌 《Building Effective Agents》가 권하는 출발점도 같은 자리입니다. 가능한 가장 단순한 해법에서 시작하고 필요할 때만 복잡도를 올리라는 것, 그리고 잘 작동한 구현은 정교한 프레임워크가 아니라 [조합 가능한 단순한 패턴]{.dot}으로 지어져 있었다는 것입니다.

주목할 점은 이것이 초보자를 위한 조언으로 제시되지 않았다는 사실입니다. 에이전트 시스템을 실제로 만들어 본 쪽에서 나온 관찰이고, 그래서 이 권고는 "아직 실력이 부족하니 작게 시작하라"가 아니라 "크게 시작하면 누구든 실패한다"는 말에 가깝습니다.

거대한 시스템을 성공적으로 AI로 빌드하는 유일한 길은 [점진적 단계별 반복(Phase-Driven Iteration)]{.dot}뿐입니다.

::: {.formula}
[점진적 단계별 반복의 세 가지 원칙]{.label}

- **한 번에 한 가지 도메인만** — 데이터베이스와 파서가 동작하기 전에 UI를 붙이지 마십시오.
- **각 단계의 '동작 증명(Proof of Working)'** — 최소한의 기능이 실제로 콘솔이나 브라우저에서 에러 없이 돌아가는 것을 확인한 뒤에야 다음 기능의 스펙을 얹어야 합니다.
- **검증된 기반 위에 얹는 레이어** — 견고한 반석(Phase 1) 위에 2층(Phase 2)을 올리고, 2층이 안전함을 확인한 뒤 3층(Phase 3)을 올려야 건물이 무너지지 않습니다.
:::

### 완벽한 명세서와 점진적 빌드는 모순되지 않는다

여기서 흔히 발생하는 오해가 있습니다.

::: {.scene}
[흔한 반문]{.label}

"앞 장에서는 4대 명세를 철저하게 사전에 작성하라면서, 여기서는 한 번에 만들지 말라니 모순 아닌가요?"
:::

전혀 모순되지 않습니다. '전체 시스템의 청사진을 미리 명확히 그리는 것'과 '그 청사진을 현실로 조립해 나가는 실행 절차'는 완전히 다른 영역입니다.

건축가는 50층짜리 빌딩의 전체 설계도를 착공 전에 완벽하게 완성해 둡니다(Spec-Driven). 하지만 공사를 진행할 때는 기초 터파기 공사가 끝나기 전에 꼭대기 층의 유리창을 주문하거나 인테리어를 하지 않습니다(Phase-Driven).

설계도는 전체를 조망하되, 그 명세서 내부의 실행 스코프는 [Phase 1: 뼈대 구축] → [Phase 2: 핵심 기능 확장] → [Phase 3: 프로덕션 배포]로 철저히 수평 분할되어야 합니다.

### 요약: 욕심을 버리는 것이 가장 빠른 지름길이다

AI라는 초고속 엔진을 손에 쥐었을 때 가장 경계해야 할 적은 기술의 한계가 아니라 개발자 내면의 조급함입니다.

한 번의 프롬프트로 유니콘을 완성하겠다는 환상을 버리십시오. 거대한 요구사항을 만나면, AI에게 한꺼번에 던지기 전에 스스로 질문해야 합니다.

::: {.callout}
"이 시스템에서 다른 모든 기능이 없어도 반드시 먼저 홀로 숨 쉬어야 하는 **'가장 작은 최소 생명체(Phase 1)'** 는 무엇인가?"
:::

다음 절에서는 4대 명세 문서 내부에서 이 단계별 경계를 어떻게 태그([Phase 1], [Phase 2], [Phase 3])로 분할하고 통제하는지 구체적인 엔지니어링 전략을 살펴보겠습니다.


## 4대 명세 문서 내부를 수평 분할하는 [Phase 1], [Phase 2], [Phase 3] 태그 전략

전체 시스템의 청사진을 한 장에 담아내면서도 AI 에이전트의 컨텍스트 오버헤드를 막는 실무적 해법은 무엇인가? 그것은 바로 4대 명세 문서(`PRD.md`, `ARCHITECTURE.md`, `DATA_SCHEMA.md`, `UI_SPEC.md`)의 각 섹션마다 명시적인 수평 분할 태그([Phase 1], [Phase 2], [Phase 3])를 부여하는 설계 전략입니다.

많은 개발자가 단계를 나눌 때 흔히 하는 실수는 '명세 파일 자체'를 `PRD_v1.md`, `PRD_v2.md`처럼 분리하는 것입니다. 파일 자체가 파편화되면 문서 간 버전 관리가 불가능해지고, 어떤 명세가 현재 유효한 기준인지 AI와 인간 모두 길을 잃게 됩니다. 단일 진실 공급원(SSOT)의 원칙을 지키려면 명세 파일은 단 4개로 유지하되, 파일 내부의 블록을 태그로 격리해야 합니다.

<!--figure: phase-tags | 파일을 쪼개지 않고 파일 안을 쪼갠다. 명세는 한 벌로 남고, 에이전트의 시야만 좁아진다.-->

### 3단계 수평 분할의 표준 정의

소프트웨어가 진화하는 생명주기에 맞추어 태그의 역할을 표준화합니다.

::: {.table-wrap}
| | **[Phase 1]** 핵심 뼈대 | **[Phase 2]** 영속성과 확장 | **[Phase 3]** 배포와 개방 |
|---|---|---|---|
| 이 단계가 끝났다는 뜻 | 시스템의 본질적 입출력이 **혼자 돈다** | 값이 **남고 다시 찾아진다** | 남이 **쓸 수 있다** |
| 들어가는 것 | 로컬 파일·인메모리 수준의 파싱과 핵심 계산 | 관계형 스키마와 마이그레이션, 검색 색인, 외부 데이터 결합 | 컨테이너 패키징, 설정 격리, 알림, 읽기 전용 개방 |
| 아직 들어가지 않는 것 | 데이터베이스, 외부 인증, 스타일링 | 배포 인프라, 외부 공개 경로 | — (여기가 마지막 층이다) |
| 완료 판정 | 핵심 계산이 실제 입력으로 **값이 맞는지** | 재적재해도 행이 **하나로 유지되는지** | 무엇을 배포했는지 **스스로 증명하는지** |
:::

가로로 읽으면 단계의 내용이 보이고, **세로로 읽으면 판정 기준이 보입니다.** 그리고 이 표에서 실무적으로 가장 자주 무시되는 칸은 세 번째 줄입니다. 무엇을 넣을지는 누구나 적지만, **무엇을 아직 넣지 않을지를 적어두지 않으면** 에이전트는 언제나 한 층 앞서 나갑니다.

### 4대 명세 문서 내 태그 적용 실례

명세서 안에서 이 태그들이 어떻게 시스템을 절단하고 격리하는지 실제 명세 템플릿의 일부로 확인해 보겠습니다.

```markdown
# 03_DATA_SCHEMA.md

## 1. Document Entity

### [Phase 1] 로컬 파싱 결과 — 메모리 내 구조체
* **id**: string (UUID v4)
* **file_path**: string (로컬 절대 경로)
* **raw_content**: string (UTF-8 마크다운 원문)
* **parsed_ast**: JSON (헤딩·코드블록 추출 노드)

---

### [Phase 2] 영속화 테이블 — documents
* **id**: UUID PRIMARY KEY DEFAULT gen_random_uuid()
* **title**: VARCHAR(255) NOT NULL
* **slug**: VARCHAR(255) NOT NULL UNIQUE
* **raw_content**: TEXT NOT NULL
* **word_count**: INTEGER NOT NULL DEFAULT 0
* **source_url**: VARCHAR(1024) NULL
* **tsv_content**: TSVECTOR GENERATED ALWAYS AS (…) STORED
* **created_at / updated_at**: TIMESTAMPTZ NOT NULL DEFAULT NOW()

---

### [Phase 3] 외부 개방 — documents를 고치지 않고 테이블을 세운다
* **api_keys** — key_hash · owner_name · is_active · rate_limit_per_minute
* **webhook_events** — event_type · payload · status · retry_count · next_retry_at
```

여기서 [Phase 3] 블록을 눈여겨보십시오. 외부 개방 기능을 붙이면서 `documents` 테이블에 `is_public`이나 `share_slug` 같은 **컬럼을 덧붙이지 않았습니다.** 대신 별도의 테이블을 세웠습니다.

이것이 단계 격리가 스키마에서 구현되는 방식입니다. [Phase 3]이 [Phase 2]의 테이블 정의를 건드리기 시작하면, 이미 검증되어 커밋된 [Phase 2]의 마이그레이션과 그 위에 세운 색인이 함께 흔들립니다. **위층을 올리려고 아래층 기둥을 옮기는 일**이고, 이 절 끝에서 다룰 두 번째 철칙이 정확히 금지하는 동작입니다.

단일 명세 파일 안에서 단계별 스키마가 이렇게 격리되어 있으면, 엔지니어는 전체 시스템이 나아갈 최종 방향을 한눈에 파악하면서도 현재 집중해야 할 경계선을 놓치지 않습니다.

### 에이전트 주입 시의 '선택적 컨텍스트 마스킹'

이 태그 전략의 진가는 Claude Code나 에이전트 CLI에 프롬프트를 주입할 때 발휘됩니다.

Phase 1을 개발할 때 명세서 전체를 통째로 던지면, AI는 Phase 2의 PostgreSQL 설정이나 Phase 3의 공유 슬러그 로직까지 미리 구현하려 들며 코드를 복잡하게 만듭니다. 이때 엔지니어는 에이전트에게 명확한 스코프 제약 지침을 전달합니다.

```bash
claude "Read docs/specs/01_PRD.md and docs/specs/03_DATA_SCHEMA.md.
Implement ONLY the items tagged with [Phase 1].
STRICTLY IGNORE all sections tagged with [Phase 2] or [Phase 3].
Do not create database connections or public share routers yet."
```

이 단 한 줄의 제약으로 인해 에이전트는 거대한 아키텍처 중에서 오직 [Phase 1] 블록만을 자신의 작업 영역으로 인식합니다.

- **컨텍스트 낭비 방지** — 불필요한 후속 기능의 추론 비용과 환각 요소를 차단합니다.
- **테스트의 명확성** — Phase 1의 요구사항에 대해서만 단위 테스트를 집중적으로 작성하고 검증합니다.
- **단방향 누적 발전** — Phase 1이 완전히 통과되어 Git 커밋으로 고정되면, 다음 세션에서 [Phase 2] 태그를 활성화하여 이미 동작이 입증된 코드베이스 위에 새로운 레이어를 안전하게 얹어 나갑니다.

### 단계 간 오염을 막는 불변의 규칙

명세 기반 단계별 빌드에서 지켜야 할 철칙은 다음과 같습니다.

::: {.formula}
[단계 격리의 두 가지 철칙]{.label}

1. **상위 단계의 하위 의존 금지** — [Phase 1]의 코드는 절대 [Phase 2]나 [Phase 3]의 컴포넌트를 import하거나 참조해서는 안 됩니다.
2. **이전 단계 코드의 파괴적 수정 금지** — [Phase 2]를 작업할 때 [Phase 1]의 핵심 파서 엔진 인터페이스를 함부로 변경해서는 안 됩니다. 확장이 필요하다면 인터페이스를 어댑터 패턴으로 감싸거나 명세 PR을 통해 하위 호환성을 검증한 뒤 수정해야 합니다.
:::

::: {.callout}
[Phase N] 태그 전략은 인간의 설계적 직관과 AI의 기계적 실행력 사이에 가장 튼튼한 방화벽을 세워주는 엔지니어링 규격입니다.
:::


## 에이전트의 컨텍스트 윈도우 통제: 작업 단위 격리와 토큰 최적화 기법

거대언어모델의 컨텍스트 윈도우(Context Window)가 100만 토큰, 200만 토큰으로 확장되면서 업계에는 또 다른 착각이 자리 잡았습니다. "컨텍스트 창이 이렇게 넓어졌으니 프로젝트의 모든 파일, 의존성 패키지, 전체 데이터베이스 덤프를 통째로 밀어 넣고 코딩을 시켜도 괜찮다"는 생각입니다.

그러나 실제 프로덕션 엔지니어링 현장에서 이는 치명적인 성능 저하와 추론 오류로 이어집니다. 컨텍스트 창의 '물리적 수용 용량'과 모델이 세부 정보를 왜곡 없이 처리하는 '유효 추론 대역폭'은 완전히 다른 문제입니다.

### '바늘 찾기(Needle In A Haystack)'의 역설과 주의력 분산

대용량 컨텍스트 벤치마크에서 모델이 수십만 토큰 속에 숨겨진 단일 텍스트(바늘)를 잘 찾아낸다고 해서, 복잡한 비즈니스 로직과 상호 의존성을 완벽히 추론할 수 있다는 의미는 아닙니다.

**컨텍스트 중앙부 정보 손실(Lost in the Middle)**

어텐션 메커니즘은 입력 텍스트의 맨 앞부분(시스템 프롬프트)과 맨 뒷부분(최근 대화)에 강한 주의를 기울입니다. 방대한 양의 소스코드가 컨텍스트 중간에 쌓이면, 중간에 위치한 명세서의 핵심 제약 조건이나 비즈니스 룰은 망각되거나 왜곡될 확률이 급격히 높아집니다.

**토큰 비용의 기하급수적 누적**

매 턴마다 불필요한 레거시 코드와 빌드 로그 수만 토큰을 반복해서 전송하면 API 비용이 폭증할 뿐 아니라, 왕복 레이턴시(Latency)가 수십 초 단위로 늘어나 실시간 개발 리듬이 완전히 깨집니다.

**잡음 증폭에 따른 환각 유발**

현재 작업과 무관한 외부 라이브러리 타입 선언이나 과거의 디버깅 콘솔 출력은 모델에게 순수한 잡음(Noise)으로 작용합니다. 모델은 이 무관한 잡음 속의 변수명이나 패턴을 끌어와 현재 코드에 엉뚱하게 결합하는 환각을 일으킵니다.

따라서 AI 네이티브 엔지니어링의 핵심 역량은 프롬프트를 화려하게 쓰는 것이 아니라, "모델의 작업 기억(Working Memory)에 들어갈 토큰을 무자비할 정도로 깎아내고 통제하는 것"입니다.

### 전략 1: 작업 단위 격리(Atomic Task Isolation)

에이전트에게 내리는 지시는 언제나 단일 책임 원칙(Single Responsibility Principle)을 준수하는 원자적 단위여야 합니다.

한 번의 세션에서 "DB 스키마를 고치고, API 라우터를 추가하고, 프론트엔드 버튼 디자인까지 바꿔라"라고 지시해서는 안 됩니다. 시스템을 기능의 수평적·수직적 원자 단위로 잘게 쪼개어 격리된 방(Room) 안에서 작업하도록 만듭니다.

<!--figure: atomic-sessions | 세션을 길게 끌수록 오염이 쌓인다. 커밋으로 끊고 새로 여는 것이 가장 값싼 컨텍스트 청소법이다.-->

각 태스크가 끝나면 에이전트의 대화 세션을 과감하게 초기화(reset 또는 새 터미널 세션)합니다.

이전 작업의 부산물은 대화 기록이 아니라 [디스크에 저장되고 커밋된 실제 파일]{.dot}로만 남깁니다. 다음 세션의 에이전트는 깨끗한 0의 상태에서 새로 시작하되, 오직 디스크에 저장된 정제된 파일들만을 읽어 들이므로 컨텍스트 오염이 원천적으로 발생하지 않습니다.

### 전략 2: 토큰 다이어트와 명세 슬라이싱(Spec Slicing)

전체 4대 명세 문서를 매번 통째로 주입하는 것도 토큰 낭비입니다. 현재 수행하려는 작업에 필요한 명세 블록만을 발췌하여 주입하는 '명세 슬라이싱' 기법을 적용해야 합니다.

::: {.table-wrap}
| 지금 하는 작업 | 올릴 것 — 왜 만드는가 | 올릴 것 — 어떤 모양인가 | 내려둘 것 |
|---|---|---|---|
| **데이터 모델링** | `01_PRD` 해당 도메인 요구사항 | `03_DATA_SCHEMA` 해당 엔티티 블록 | `02_ARCHITECTURE` · `04_UI_SPEC` |
| **API 구현** | `02_ARCHITECTURE` 해당 계층 | `03_DATA_SCHEMA` 해당 계약(Contract) | `01_PRD` · `04_UI_SPEC` |
| **UI 컴포넌트 구현** | `04_UI_SPEC` 해당 컴포넌트 스펙 | `03_DATA_SCHEMA` 응답 인터페이스 | `01_PRD` · `02_ARCHITECTURE` |
| **배포·인프라** | `01_PRD` 비기능 요구사항(가용성·보존) | `02_ARCHITECTURE` 배포 토폴로지·환경 변수 규격 | `03_DATA_SCHEMA` · `04_UI_SPEC` |
:::

세로로 읽으면 규칙이 하나로 보입니다. **한 작업에 올라가는 문서는 언제나 둘이고, 나머지 둘은 내려둡니다.**

그리고 그 둘은 아무 둘이 아닙니다. 하나는 **왜 만드는지**를 말하는 문서이고 다른 하나는 **어떤 모양이어야 하는지**를 말하는 문서입니다. 의도만 주면 에이전트는 형식을 지어내고, 형식만 주면 무엇을 위한 것인지 모른 채 규격을 채웁니다. 짝이 맞아야 합니다.

`03_DATA_SCHEMA`가 네 행 중 세 행에 등장하는 것도 우연이 아닙니다. 데이터의 모양은 거의 모든 작업의 접점이고, 그래서 이 문서만이 여러 작업에 반복해서 올라갑니다. 제5장에서 스키마 명세를 "가장 강력한 환각 방지 가드레일"이라 부르는 근거가 이 표에 이미 나와 있습니다.

이처럼 작업과 무관한 명세와 코드를 철저히 배제하면, 모델에 전달되는 컨텍스트가 현재 작업과 직결된 정보로만 채워집니다. 정보의 밀도가 극대화되면 모델의 어텐션은 분산되지 않고 날카로운 면도날처럼 동작합니다.

### 전략 3: 리포지토리 맵(Repository Map)과 인터페이스 요약본 활용

거대한 레거시 프로젝트나 수백 개의 모듈이 존재하는 환경에서는 소스코드 파일 전체를 읽히는 대신, 시그니처와 인터페이스만 추출한 뼈대 문서를 생성해 주입합니다.

구현 세부사항(함수 내부의 루프문, 알고리즘 연산)은 지우고, 클래스명, 메서드 시그니처, 파라미터 타입, 주석만 남긴 `.d.ts` 또는 인터페이스 요약 스켈레톤을 컨텍스트로 제공합니다.

에이전트는 수천 줄의 코드를 읽지 않고도 전체 시스템의 모듈 간 결합 관계와 호출 규격을 시그니처 요약본만으로 즉시 파악합니다.

### 요약: 비워낼수록 정밀해진다

AI 네이티브 개발에서 생산성을 결정짓는 핵심은 "얼마나 많은 정보를 AI에게 밀어 넣는가"가 아니라 "얼마나 불필요한 잡음을 덜어내고 순수한 본질만 남겨 전달하는가"입니다.

::: {.worksheet}
#### 컨텍스트를 깎아내는 세 가지 습관

1. 대화창에 의존하지 말고, 검증된 작업 단위마다 Git 커밋 후 세션을 리셋하십시오.
2. 현재 작업에 반드시 필요한 명세 블록만 슬라이싱하여 컨텍스트에 올리십시오.
3. 구현체가 아닌 엄격한 인터페이스와 타입 규격으로 에이전트의 시야를 제한하십시오.
:::

::: {.callout}
작업 단위를 철저히 격리하고 토큰을 통제할 때, AI 에이전트는 컨텍스트의 미로에서 방황하지 않고 단 한 번의 호출로 완벽히 정렬된 코드를 직조해 냅니다.
:::
