## 패턴 1 & 2: 프롬프트 체이닝(Prompt Chaining)과 지능형 라우팅(Routing)

앤스로픽(Anthropic)이 공식 연구 보고서 《Building Effective Agents》에서 가장 강하게 경고하는 아키텍처적 오류는 "단 하나의 거대한 범용 에이전트에게 모든 것을 맡기는 것"입니다.

하나의 프롬프트 안에서 문서를 분석하고, 아키텍처를 결정하며, 데이터베이스 쿼리를 짜고, 프론트엔드 코드까지 한 번에 완성하려는 시도는 실패할 수밖에 없습니다. 모델이 아무리 뛰어난 지능을 갖추었더라도, 단일 추론 스텝에 너무 많은 인지적 부하(Cognitive Load)가 가해지면 오류율이 가파르게 증가합니다.

앤스로픽이 제시하는 고신뢰도 에이전트 시스템의 출발점은 복잡한 작업을 명확한 단위로 직렬 분해하는 [프롬프트 체이닝(Prompt Chaining)]{.dot}과, 입력의 성격에 따라 최적의 전문 파이프라인으로 작업을 분기하는 [지능형 라우팅(Routing)]{.dot}입니다.

### 패턴 1: 프롬프트 체이닝 — 직렬 파이프라인의 힘

프롬프트 체이닝은 복잡한 작업을 '순차적인 하위 작업(Sub-tasks)'의 연결로 분해하고, 이전 단계의 출력이 프로그래밍 방식으로 검증(Gate)된 후에만 다음 단계의 입력으로 주입되는 아키텍처입니다.

<!--figure: prompt-chaining | 체이닝의 핵심은 단계가 아니라 단계 사이다. 검증 게이트가 없으면 그것은 그냥 긴 프롬프트다.-->

체이닝의 핵심은 단순히 프롬프트를 이어 붙이는 것이 아니라, 단계와 단계 사이에 '프로그래밍 방식의 검증 게이트(Programmatic Gate)'를 배치한다는 점입니다.

::: {.formula}
[검증 게이트가 만들어내는 세 가지 이득]{.label}

- **실패의 조기 격리(Early Failure Isolation)** — Step 1에서 잘못된 데이터가 추출되었다면 Step 2로 넘어가지 않고 그 자리에서 즉각 중단하거나 재시도합니다.
- **추론 집중도 극대화** — 각 단계의 LLM은 오직 단 하나의 작업(Single Concern)에만 어텐션을 온전히 집중하므로 정밀도가 비약적으로 상승합니다.
- **투명한 디버깅** — 파이프라인 중 어느 구간에서 규격 위반이 발생했는지 로그를 통해 정확히 추적할 수 있습니다.
:::

#### 실전 적용 예시: 마크다운 아카이브의 수집 파이프라인

우리 프로젝트인 지식 아카이브 SaaS에서 웹 아티클을 수집할 때 체이닝은 다음과 같이 작동합니다.

::: {.scene}
[수집 체인]{.label}

1. **Step 1 (정제 체인)** — 원시 HTML에서 광고, 내비게이션 태그를 제거하고 순수 본문 텍스트만 마크다운으로 변환.
2. **Gate (검증)** — 추출된 텍스트가 100단어 이상인지, 유효한 UTF-8 문자열인지 정규식·코드로 검증.
3. **Step 2 (구조화 체인)** — 정제된 마크다운을 분석하여 `03_DATA_SCHEMA.md`에 정의된 규격대로 Title, Slug, Tags 배열을 JSON 형태로 추출.
:::

### 패턴 2: 지능형 라우팅 — 관심사 분리와 전문화

라우팅은 입력을 먼저 분석하여 그 의도(Intent)나 복잡도에 따라 가장 적합한 전문 프롬프트, 도구, 혹은 경량 모델로 분기(Branching)시키는 패턴입니다.

모든 요청을 가장 무겁고 비싼 상위 추론 모델의 복잡한 프롬프트로 처리할 필요는 없습니다. 단순 오타 수정이나 날짜 포맷 변환 같은 경량 작업은 경량 고속 모델로 보내고, 고난도의 아키텍처 설계나 SQL 튜닝만 심층 분석 체인으로 보내는 것이 비용과 속도 모두에서 압도적으로 유리합니다.

<!--figure: agent-routing | 모든 요청을 가장 비싼 경로로 보낼 이유는 없다. 라우터는 비용과 속도를 동시에 사는 장치다.-->

#### 라우터 설계의 세 가지 핵심 원칙

::: {.formula}
[라우터 설계 원칙]{.label}

1. **명확한 분류 기준(Distinct Taxonomy)** — 각 분기 경로는 상호 배타적(Mutually Exclusive)이어야 합니다. 라우터가 갈피를 잡지 못하고 애매하게 중간에 걸치는 일이 없도록 분기 카테고리를 엄밀히 정의합니다.
2. **경량성(Lightweight)** — 라우팅 자체가 무거워져서는 안 됩니다. 정규식(Regex)이나 키워드 매칭으로 분기할 수 있다면 굳이 LLM을 쓰지 않고, 자연어 의도 파악이 필요할 때만 최소한의 토큰으로 분류 전용 프롬프트를 구동합니다.
3. **폴백(Fallback) 안전장치** — 분류 신뢰도가 임계치(예: 80%) 이하일 경우 기본 안전 경로(Default Fallback Branch)로 우회시켜 처리 누락을 방지합니다.
:::

### 체이닝과 라우팅의 결합: 엔터프라이즈급 인제스천 엔진

실제 프로덕션 레벨에서는 라우팅과 체이닝이 유기적으로 결합합니다.

<!--figure: router-chains | 라우팅은 어느 체인으로 갈지 정하고, 체인은 그 안에서 무엇을 할지 정한다. 두 결정은 층이 다르다.-->

라우터가 입력 데이터의 유형을 판별하여 최적의 파이프라인으로 작업을 밀어 넣어주면, 각 체인은 오직 자신에게 주어진 명세에만 집중하여 오류 없이 순차 작업을 완결합니다.

### 요약: 단일 프롬프트의 한계를 넘어서는 공학적 해법

"하나의 프롬프트로 기적을 만들겠다"는 생각을 버려야 합니다.

::: {.callout}
복잡한 비즈니스 로직을 마주했을 때 엔지니어가 해야 할 일은, 모델에게 긴 프롬프트를 주며 기도하는 것이 아닙니다. 문제를 순차적 체인(Chaining)으로 쪼개고, 상황에 맞는 최적의 경로(Routing)를 깔아주는 것입니다.
:::

이 두 가지 기본 패턴이 튼튼하게 자리 잡을 때, 다음 절에서 다룰 대규모 병렬화(Parallelization)와 오케스트레이터-워커(Orchestrator-Workers) 아키텍처가 비로소 제 힘을 발휘하게 됩니다.


## 패턴 3 & 4: 명세 섹셔닝 병렬화(Parallelization)와 오케스트레이터-워커(Orchestrator-Workers)

프롬프트 체이닝이 '직렬적 깊이'를 해결하고 라우팅이 '전문적 분기'를 담당한다면, 대규모 엔터프라이즈 시스템 구축에서 속도와 확장성을 폭발시키는 열쇠는 [병렬화(Parallelization)]{.dot}와 [오케스트레이터-워커(Orchestrator-Workers)]{.dot} 패턴입니다.

수십 개의 API 엔드포인트와 복잡한 프론트엔드 컴포넌트, 그리고 수백 개의 테스트 케이스를 하나의 에이전트가 순차적으로 작성하게 두면 수십 분에서 수 시간이 소요될 뿐만 아니라, 뒤로 갈수록 이전 작업의 맥락을 잊어버리는 성능 저하가 발생합니다. 작업을 직렬로 늘어놓지 않고 독립적인 슬라이스로 쪼개어 동시에 처리하는 고급 분산 에이전트 아키텍처가 필요한 이유입니다.

### 패턴 3: 명세 섹셔닝 병렬화

병렬화는 하나의 작업을 독립적인 여러 하위 작업으로 쪼갠 뒤, 여러 에이전트 인스턴스에 동시에 분배하여 처리 속도를 비약적으로 끌어올리고 결과를 취합(Aggregate)하는 패턴입니다. 앤스로픽은 이를 크게 두 가지 방식으로 정의합니다.

::: {.formula}
[병렬화의 두 갈래]{.label}

- **섹셔닝(Sectioning)** — 거대한 작업을 서로 겹치지 않는 독립적인 영역들로 물리적으로 분할하여 동시에 실행하는 방식.
- **투표(Voting / Ensembling)** — 동일한 태스크를 각기 다른 프롬프트나 샘플링 온도로 여러 에이전트에게 동시에 풀게 한 뒤, 다수결이나 교차 검증을 통해 최선의 정답을 채택하는 방식.
:::

소프트웨어 엔지니어링에서 가장 강력한 위력을 발휘하는 것은 바로 [명세 섹셔닝(Spec Sectioning)]{.dot}입니다.

<!--figure: spec-sectioning | 겹치지 않게 자르는 것이 전부다. 경계가 명확하면 병렬은 공짜로 얻어진다.-->

#### 실전 적용: API 라우터의 병렬 섹셔닝

우리 프로젝트의 백엔드 API 명세가 다음과 같이 정의되어 있다고 가정해 보겠습니다.

- **Router 1** — 인증 및 사용자 세션 API (`/api/v1/auth/*`)
- **Router 2** — 마크다운 문서 CRUD API (`/api/v1/documents/*`)
- **Router 3** — 태그 및 메타데이터 필터링 API (`/api/v1/tags/*`)

이 세 영역은 서로의 내부 구현을 직접 참조하지 않으며, 오직 `03_DATA_SCHEMA.md`에 선언된 공통 타입 인터페이스(`@shared/types`)만을 바라봅니다.

엔지니어는 단일 세션에서 세 라우터를 차례대로 짜게 할 필요가 없습니다. 3개의 독립된 에이전트(혹은 프로세스)를 띄워 각 라우터를 동시에 생성하게 합니다. 세 라우터가 모두 작성되면, 컴파일러(`tsc`)와 린터가 이를 하나로 묶어 결합 무결성을 검증합니다. 순차로 짜던 백엔드 스켈레톤 구축 시간이, 세 라우터를 합한 시간이 아니라 가장 오래 걸리는 라우터 하나의 시간으로 수렴합니다.

### 패턴 4: 오케스트레이터-워커

병렬화가 '사전에 엔지니어가 작업 단위를 딱딱 쪼개어 놓은 고정된 분할'이라면, 오케스트레이터-워커(Orchestrator-Workers)는 시스템의 복잡도가 높아 작업의 범위와 분할 계획 자체를 중앙 지능(Orchestrator)이 동적으로 수립해야 할 때 사용하는 진화된 아키텍처입니다.

중앙의 오케스트레이터 LLM은 직접 코드를 작성하지 않습니다. 오케스트레이터의 유일한 책무는 '작업 분석, 하위 태스크 분해, 전문 워커 에이전트 소환, 그리고 최종 결과의 정합성 종합'입니다.

<!--figure: orchestrator-workers | 지휘자는 악기를 연주하지 않는다. 오케스트레이터가 코드를 짜기 시작하면 그 구조는 이미 무너진 것이다.-->

#### 오케스트레이터-워커의 3단계 오퍼레이션 사이클

::: {.formula}
[오퍼레이션 사이클]{.label}

1. **계획 수립(Planning)** — 오케스트레이터가 `01_PRD.md`와 `02_ARCHITECTURE.md`를 읽고 비순환 방향 그래프(DAG, Directed Acyclic Graph) 형태의 실행 계획을 세웁니다. "Worker 1이 DB 마이그레이션 스크립트를 작성하면, Worker 2와 Worker 3이 그 스키마를 바탕으로 API 라우터와 단위 테스트를 동시에 작성한다."
2. **워커 디스패치(Worker Dispatching)** — 각 하위 태스크에 특화된 워커 에이전트에게 '극도로 슬라이싱된 최소 컨텍스트'만을 주입하여 작업을 위임합니다. 워커 1은 오직 `03_DATA_SCHEMA.md`만 보고 DDL을 생성하고, 워커 3은 오직 `04_UI_SPEC.md`만 보고 UI 뷰어를 조립합니다. 워커들끼리는 서로의 존재를 알 필요가 없습니다.
3. **종합 및 충돌 해결(Synthesis)** — 각 워커가 반환한 코드 조각들을 오케스트레이터가 회수합니다. 오케스트레이터는 전체 아키텍처 관점에서 파일 경로, 모듈 임포트 구문, 환경 변수 참조가 완벽히 일치하는지 최종 검토하고 디스크에 커밋합니다.
:::

### 언제 어떤 패턴을 선택해야 하는가?

팀과 프로젝트의 상황에 따라 적절한 패턴을 선택할 수 있어야 합니다.

::: {.table-wrap}
| 비교 항목 | 명세 섹셔닝 병렬화 (Pattern 3) | 오케스트레이터-워커 (Pattern 4) |
|---|---|---|
| 작업 분할 주체 | 인간 엔지니어 (정적 분할) | 오케스트레이터 LLM (동적 분할) |
| 적합한 상황 | 도메인 경계가 명확한 기능 동시 구현 (예: 5개 API 라우터 일괄 개발) | 미지의 문제 분석, 대규모 리팩토링, 복합 시스템 마이그레이션 |
| 컨텍스트 제어 | 각 작업별로 엔지니어가 직접 명세 주입 | 중앙 모델이 하위 워커에 컨텍스트를 동적으로 배분 |
| 구현 복잡도 | 낮음 (쉘 스크립트나 병렬 CLI로 즉시 가능) | 높음 (작업 큐, 상태 추적, 재시도 제어 엔진 필요) |
:::

### 요약: 단일 일꾼에서 오케스트라의 지휘자로

AI 에이전트를 다루는 엔지니어의 위상은 '직접 삽을 들고 땅을 파는 일꾼'에서, 수많은 전문 일꾼들에게 도면의 일부를 나누어주고 공정을 관리하는 '현장 총괄 소장(Orchestrator)'으로 진화해야 합니다.

::: {.callout}
명세서를 독립된 영역으로 수평 분할(Sectioning)하여 동시에 실행하고, 복잡한 프로젝트를 오케스트레이터에게 위임하여 워커들을 지휘하게 만드십시오. 이때 발생하는 속도의 혁신은 혼자서 코딩하던 시절과는 비교할 수 없는 압도적인 엔지니어링 생산성을 안겨줄 것입니다.
:::

다음 절에서는 이 워크플로우의 완결판이자, 스스로 코드를 채점하고 에러를 수정하는 '평가기-최적화기(Evaluator-Optimizer)' 루프를 다루겠습니다.


## 패턴 5: 평가기-최적화기(Evaluator-Optimizer) 루프를 통한 자동 단위 테스트 및 자가 교정

AI 에이전트가 코드를 작성하는 과정에서 가장 흔하게 발생하는 병목은 '인간의 피드백 루프'입니다.

에이전트가 코드를 출력하면, 개발자가 터미널에서 `npm test`나 `pytest`를 직접 실행하고, 빨간색 에러 로그를 긁어 복사한 뒤, 다시 대화창에 붙여 넣으며 "에러 났으니 고쳐줘"라고 타이핑합니다. 이 수동 핑퐁은 개발자를 끊임없이 지치게 만들며, 앞 장에서 경고했던 대화형 컨텍스트 오염을 재현합니다.

앤스로픽이 정의하는 가장 진보된 자율 에이전트 루프, 즉 평가기-최적화기(Evaluator-Optimizer) 패턴은 이 지루한 인간 검수 과정을 완전히 제거합니다. 코드를 작성하는 주체(Optimizer/Generator)와 이를 엄격한 명세에 비추어 채점하는 주체(Evaluator)를 시스템적으로 분리하고, 테스트가 100% 통과할 때까지 스스로 비판하고 자가 교정(Self-Correction)하는 닫힌 루프(Closed-Loop)를 구축하는 것입니다.

### 생성자와 평가자의 분리(The Dual-Agent Dynamic)

인간 개발자도 자신이 방금 작성한 코드의 버그를 찾는 데 어려움을 겪습니다. 인지적 편향(Confirmation Bias) 때문에 자신의 논리적 맹점을 보지 못하기 때문입니다. AI 모델 역시 마찬가지입니다. 단일 에이전트에게 "코드를 짜고, 검토까지 끝내라"고 요구하면, 모델은 자신이 방금 내린 가정을 맹목적으로 신뢰하며 결함을 지나칩니다.

평가기-최적화기 패턴은 이 문제를 [역할의 적대적 분리]{.dot}로 해결합니다.

<!--figure: evaluator-optimizer | 자기가 쓴 코드를 자기가 채점하면 편향이 남는다. 채점자는 명세를 든 다른 주체여야 한다.-->

::: {.formula}
[두 역할의 책무]{.label}

- **생성자(Optimizer/Generator)** — 주어진 명세를 바탕으로 가장 빠르고 간결하게 구현 코드를 생산합니다.
- **평가자(Evaluator)** — 코드를 작성하지 않습니다. 오직 명세서에 정의된 계약(Contract)과 제약 조건을 기준으로 제출된 코드를 냉혹하게 채점합니다. 평가자는 LLM일 수도 있고, 결정론적인 정적 분석기(TypeScript Compiler, ESLint, Jest/Pytest)일 수도 있습니다.
:::

### 결정론적 도구(Deterministic Tools)를 평가자로 결합하기

앤스로픽 엔지니어링 표준에서 권장하는 가장 이상적인 평가자는 '또 다른 LLM'이 아니라, 기계적인 컴파일러와 단위 테스트 러너입니다.

LLM 평가자는 주관적 해석의 여지가 있지만, 컴파일러와 테스트 러너는 거짓말을 하지 않습니다. 코드가 명세를 위반하면 실패(Exit code 1)하고, 만족하면 성공(Exit code 0)합니다.

#### 실전 자가 교정 루프의 4단계 라이프사이클

**1. 생성(Generate)**

에이전트가 `03_DATA_SCHEMA.md`를 바탕으로 마크다운 파서 및 캐싱 모듈 코드를 작성하여 파일로 저장합니다.

**2. 평가(Evaluate)**

에이전트 러너(CLI)가 즉시 백그라운드에서 단위 테스트 스크립트를 실행합니다.

```bash
npm run test:unit -- --json --outputFile=test-results.json
```

**3. 피드백 파싱(Feedback Extraction)**

테스트가 실패하면, 전체 콘솔 출력 중 잡음을 제거하고 실패한 테스트 케이스의 이름, 기댓값(Expected), 실제값(Received), 스택 트레이스만 정밀하게 추출합니다.

**4. 최적화 및 자가 교정(Optimize)**

에이전트에게 사람이 개입하지 않고 정제된 에러 피드백을 전달합니다.

::: {.scene}
[정제된 피드백]{.label}

"테스트 케이스 `should parse frontmatter with empty tags array`가 실패했습니다. 기댓값은 `[]`이나 `null`이 반환되었습니다. `parser.ts`의 42번째 줄을 수정하여 다시 통과시키십시오."
:::

에이전트는 이 피드백을 보고 즉시 타겟 코드를 패치한 뒤 다시 테스트를 돌립니다. 이 루프는 테스트 결과가 올그린(All Green)이 될 때까지 최대 허용 횟수(Max Iterations, 보통 3~5회) 내에서 완전 자동으로 반복됩니다.

### 평가기-최적화기가 적용된 지식 아카이브 테스트 하네스

우리 실전 프로젝트인 마크다운 지식 아카이브 SaaS의 파서 엔진에 이 패턴을 적용한 실제 프롬프트 및 실행 구조는 다음과 같습니다.

```markdown
### [Self-Correction Task Directive]

1. **Target**: `src/core/markdown-parser.ts`
2. **Specification SSOT**: `docs/specs/03_DATA_SCHEMA.md` Section 1 [Phase 1]
3. **Evaluation Command**: `npm test tests/unit/parser.test.ts`
4. **Loop Constraints**:
   - 테스트 실패 시 대화창에 사과하거나 설명을 늘어놓지 말 것.
   - 테스트 러너의 실패 스택 트레이스를 분석하여 파일의 해당 라인만 직접 수정할 것.
   - `tests/unit/parser.test.ts` 자체를 수정하여 테스트를 통과시키는 행위는
     엄격히 금지됨 (명세 훼손 금지).
   - 모든 테스트가 100% Pass할 때만 "ALL UNIT TESTS PASSED"라는 단일 라인을
     출력하고 종료할 것.
```

이 지침이 내려지면 에이전트는 마치 스스로 TDD(Test-Driven Development)를 수행하는 시니어 엔지니어처럼 행동합니다. 자신이 짠 코드의 결함을 스스로 발견하고, 2~3회의 루프 만에 버그 없는 견고한 코드로 담금질해 냅니다.

### 인간 엔지니어의 위치: '채점표(Rubric)'의 설계자

평가기-최적화기 패턴이 완성되면, 인간 개발자의 노동은 완전히 다른 차원으로 승격됩니다.

우리는 더 이상 코드를 고치느라 터미널과 에디터를 오가지 않습니다. 대신 "평가자가 사용할 테스트 케이스와 평가 기준(Rubric)을 얼마나 빈틈없이 짤 것인가"에 집중합니다.

엣지 케이스, 경계값(Boundary values), 보안 취약점 시나리오를 단위 테스트로 꼼꼼하게 선언해 두기만 하면, 구현과 디버깅이라는 고통스러운 작업은 에이전트의 자가 교정 루프가 넘겨받습니다.

### 요약: 무결점 코드를 향한 닫힌 제어계

소프트웨어 공학에서 제어계(Control System)가 안정적으로 동작하려면 출력 결과를 센서로 측정해 입력으로 되먹이는 피드백 루프(Closed Loop)가 필수적입니다.

::: {.callout}
코드를 한 번 짜고 끝내는 것은 개루프(Open Loop)이며, 환각과 에러에 취약합니다.

코드를 생성하고, 기계적 테스트로 평가하며, 결함을 스스로 수정하는 평가기-최적화기(Evaluator-Optimizer)는 자율적으로 수렴하는 진정한 폐루프(Closed Loop) 공학입니다.
:::

이로써 앤스로픽의 공식 5대 에이전트 워크플로우(체이닝, 라우팅, 병렬화, 오케스트레이터, 평가기 루프)가 모두 정리되었습니다. 이제 다음 장에서는 이러한 고차원 추론 두뇌를 현실의 시스템 및 도구와 결합하는 기술 표준, Model Context Protocol(MCP)의 세계로 진입하겠습니다.
