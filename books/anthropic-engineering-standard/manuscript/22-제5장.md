## 03_DATA_SCHEMA.md: 시스템의 뼈대 — 타입 무결성 DDL, 관계형 모델, API/Webhook 스키마

소프트웨어 시스템에서 비즈니스 로직과 UI는 유행과 기획에 따라 끊임없이 바뀝니다. 하지만 한 번 잘못 설계되어 데이터베이스에 적재된 데이터 스키마는 마이그레이션에 천문학적인 비용이 들며, 시스템 전체를 주저앉히는 시한폭탄이 됩니다.

리누스 토발즈(Linus Torvalds)의 유명한 격언처럼, "나쁜 프로그래머는 코드를 걱정하지만, 좋은 프로그래머는 데이터 구조와 그 관계를 걱정합니다."

AI 네이티브 개발 환경에서 이 격언은 더욱 치명적인 진실이 됩니다. AI 에이전트에게 데이터베이스와 인터페이스의 타입을 정밀하게 선언해주지 않으면, 모델은 필드명을 제멋대로 축약하고, 외래 키 제약 조건을 누락하며, 널(Null) 처리를 빠뜨려 런타임 데이터 오염을 양산합니다.

`03_DATA_SCHEMA.md`는 시스템의 가장 단단한 뼈대이자, 에이전트가 생성하는 모든 SQL 쿼리, ORM 엔티티, API 직렬화 로직을 통제하는 [타입 무결성의 단일 진실 공급원]{.dot}입니다.

### 타입 무결성 DDL(Data Definition Language)의 사전 선언

자연어로 "사용자 테이블과 문서 테이블을 만들고 연결해줘"라고 지시하는 것은 재앙의 시작입니다.

에이전트는 `id`를 어떤 곳에서는 정수형 오토인크리먼트(`BIGSERIAL`)로, 다른 테이블에서는 문자열 UUID(`VARCHAR(36)`)로 정의하여 조인(Join) 성능을 망가뜨릴 수 있습니다. 또한 `created_at` 컬럼에 타임존 정보(`TIMESTAMPTZ`)를 빼먹어 다국적 서비스 배포 시 심각한 시계열 오차를 유발합니다.

`03_DATA_SCHEMA.md`에서는 자연어 요약에 머무르지 않고, 실제 프로덕션에 적용 가능한 수준의 완전한 표준 SQL DDL 구문을 명세서 내부에 직접 포함해야 합니다.

::: {.formula}
[DDL 사전 선언의 네 가지 표준]{.label}

- **고유 식별자(PK) 표준화** — 모든 테이블의 기본 키를 UUID v4(`gen_random_uuid()`) 또는 분산 정렬 가능한 CUID/ULID로 일관되게 규정.
- **불변 감사 필드(Audit Fields)** — 모든 테이블에 `created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`, `updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()` 강제.
- **명시적 삭제 정책** — 참조 무결성 유지를 위해 외래 키에 `ON DELETE CASCADE` 또는 `ON DELETE RESTRICT` 명시.
- **복합 인덱스 및 검색 인덱스** — 쿼리 패턴을 미리 예측하여 자주 조회되는 컬럼의 인덱스 선언.
:::

### 관계형 모델과 단계별(Phase-Driven) 진화

`03_DATA_SCHEMA.md` 역시 앞서 다룬 단계별 태그([Phase 1], [Phase 2], [Phase 3]) 전략을 따라야 합니다. 데이터 구조를 처음부터 완벽한 거대 분산 DB 형태로 선언하면, MVP를 구현하는 에이전트가 로컬 파일 시스템 작업 중에도 복잡한 DB 트랜잭션 코드를 짜려 드는 부작용이 발생합니다.

- [Phase 1] — 메모리 및 로컬 파일 기반 스키마 (TypeScript Interface 중심)
- [Phase 2] — 영속성 관계형 데이터베이스 DDL 및 전문 검색 인덱스 (PostgreSQL / SQLite)
- [Phase 3] — 외부 공유 권한 플래그, B2B Webhook 이벤트 및 API 키 인증 스키마

# 03_DATA_SCHEMA: Data Models, DDL & Contract Specifications

### [Phase 1] Local In-Memory & File TypeScript Types
백엔드 DB 없이 로컬 파일 시스템 파싱 시 사용하는 핵심 메모리 인터페이스.

```typescript
export interface LocalDocumentNode {
  id: string;                 // 파일 경로 기반 SHA-256 해시값 (앞 12자리)
  filePath: string;           // 파일의 상대 경로 ("vault/tech/docker.md")
  title: string;              // Frontmatter 제목 또는 파일의 첫 번째 H1
  rawContent: string;         // UTF-8 마크다운 원문
  tags: string[];             // Frontmatter의 tags 배열 (공백 제거)
  wordCount: number;          // 공백 제외 단어 수
  lastModifiedAt: string;     // ISO 8601 형식의 파일 수정 시간
}
```

### [Phase 2] Relational Database Schema (PostgreSQL DDL)
Phase 2 데이터베이스 마이그레이션 시 실행할 표준 DDL.

```sql
-- 확장 모듈 활성화
CREATE EXTENSION IF NOT EXISTS "pgcrypto";

-- 문서 영속화 테이블
CREATE TABLE documents (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    title VARCHAR(255) NOT NULL,
    slug VARCHAR(255) NOT NULL UNIQUE,
    raw_content TEXT NOT NULL,
    html_cache TEXT NULL,
    word_count INTEGER NOT NULL DEFAULT 0,
    source_url VARCHAR(1024) NULL,
    tsv_content TSVECTOR GENERATED ALWAYS AS (
        to_tsvector('simple', coalesce(title, '') || ' ' || coalesce(raw_content, ''))
    ) STORED,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- 태그 테이블 및 다대다 매핑
CREATE TABLE tags (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name VARCHAR(50) NOT NULL UNIQUE
);

CREATE TABLE document_tags (
    document_id UUID NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
    tag_id UUID NOT NULL REFERENCES tags(id) ON DELETE CASCADE,
    PRIMARY KEY (document_id, tag_id)
);

-- 전문 검색 및 인덱스 최적화
CREATE INDEX idx_documents_tsv ON documents USING GIN(tsv_content);
CREATE INDEX idx_documents_created_at ON documents (created_at DESC);
```

### [Phase 3] External Share, API Keys & Webhook Schema

```sql
-- 외부 B2B 시스템 연동을 위한 API Key 관리 테이블
CREATE TABLE api_keys (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    key_hash VARCHAR(64) NOT NULL UNIQUE,  -- SHA-256 해시 저장 (원문 저장 금지)
    owner_name VARCHAR(100) NOT NULL,
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    rate_limit_per_minute INT NOT NULL DEFAULT 60,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- 외부 웹훅 발송 큐 테이블
CREATE TABLE webhook_events (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    event_type VARCHAR(50) NOT NULL,       -- "document.created", "document.updated"
    payload JSONB NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING', -- PENDING, DELIVERED, FAILED
    retry_count INT NOT NULL DEFAULT 0,
    next_retry_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

### 데이터 스키마가 완벽할 때 일어나는 기적

이 명세 파일이 프로젝트에 존재하는 순간, 백엔드 엔지니어링의 불확실성이 크게 줄어듭니다.

- **DB 마이그레이션의 자동화** — 에이전트에게 "Phase 2 DDL을 읽고 Prisma 스키마 또는 TypeORM 엔티티 파일을 생성하라"고 지시하면, 오타나 관계 누락 없이 모델 코드가 곧바로 추출됩니다.
- **타입 안전성(End-to-End Type Safety)** — 명세서에 선언된 TypeScript 인터페이스를 클라이언트와 서버가 직접 공유함으로써, API 응답 객체를 파싱할 때 생기는 타입 불일치가 컴파일 단계에서 드러납니다.
- **보안과 감사의 표준화** — API 키의 해시 저장(`SHA-256`) 원칙이나 웹훅 재시도 큐가 DDL 수준에서 고정되어 있어, AI가 보안적으로 취약한 플레인 텍스트 저장 방식을 채택하는 사고를 원천 차단합니다.

::: {.callout}
결국 코드는 데이터의 형태를 따라 흐를 뿐입니다. 데이터 구조가 엄밀하게 정의되어 있다면, 그 위에 올라가는 비즈니스 로직은 누구나 쉽게, 그리고 AI는 완벽하게 작성해 낼 수 있습니다.
:::


## 왜 데이터 스키마가 에이전트의 가장 강력한 환각 방지 가드레일인가

<!-- ⚠ 문장은 초안이다. 저자의 목소리로 다시 쓸 것. 사실·수치는 전부 실측 근거 있음. -->

환각을 막는 방법으로 가장 먼저 떠올리는 것은 프롬프트입니다. "지어내지 마라", "모르면 모른다고 하라", "반드시 사실에 근거하라". 이런 문장을 아무리 정교하게 다듬어도 환각은 줄어들 뿐 사라지지 않습니다.

이유는 단순합니다. **환각은 모델이 나쁜 값을 고르는 사건이 아니라, 고를 수 있는 값이 너무 많을 때 생기는 사건입니다.** 자유도가 문제입니다. 그리고 자유도를 줄이는 가장 강력한 장치가 데이터 스키마입니다.

`03_DATA_SCHEMA.md`는 에이전트에게 무엇을 만들지 알려주는 문서가 아닙니다. **무엇을 만들 수 없는지 알려주는 문서**입니다.

### 환각이 데이터로 들어오는 세 경로

실제로 잘못된 값이 시스템에 들어오는 길은 셋뿐입니다. 각각을 스키마의 어느 층이 막는지가 다릅니다.

::: {.formula}
[환각의 세 경로]{.label}

1. **없는 필드를 지어낸다** — 응답 객체에 `status`나 `is_verified` 같은 필드가 슬며시 생긴다. 아무도 정의한 적이 없는데 그럴듯해서 붙는다.
2. **있는 필드를 다른 의미로 쓴다** — 타입도 이름도 맞는데 담긴 값의 의미가 다르다. **가장 잡기 어렵다.** 컴파일러도 스키마 검증도 통과한다.
3. **없는 값을 채운다** — 결측을 `0`이나 빈 문자열이나 직전 값으로 메운다. 없는 데이터가 있는 데이터의 얼굴을 하고 들어온다.
:::

1번은 스키마가 **닫혀** 있으면 막힙니다. 필드 목록이 열거되어 있고 "여기 없는 것은 없다"가 선언되어 있으면 에이전트는 새 필드를 만들지 못합니다.

3번은 스키마에 **없을 때 무엇으로 두는지**가 적혀 있으면 막힙니다. "직전 분기 누계가 없으면 값을 지어내지 말고 `None`" 같은 한 줄입니다.

문제는 2번입니다.

### 타입 무결성은 의미 무결성을 보장하지 않는다

이 책이 스키마를 독립 문서로 올려야 한다고 말하는 진짜 이유가 여기 있습니다.

같은 타입을 가진 두 값이 완전히 다른 의미일 수 있습니다. 어떤 정적 타입 검사도, 어떤 JSON 스키마 검증도 이 둘을 구분해 주지 않습니다.

::: {.table-wrap}
| 두 값 | 타입 | 실제 의미 | 잘못 쓰면 |
|---|---|---|---|
| 분기 당기금액 vs 누계금액 | 둘 다 숫자 | 3개월 실적 vs 연초 이후 누적 | 성장률이 통째로 틀린다 |
| 손익 항목 vs 재무상태 항목 | 둘 다 숫자 | 기간 발생액(유량) vs 시점 잔액(저량) | 차분하면 값이 망가진다 |
| 수집 시각 vs 공시 시각 | 둘 다 타임스탬프 | 우리가 본 때 vs 시장에 나온 때 | 시계열이 미래를 참조한다 |
| 결측 vs 0 | 둘 다 숫자 | 자료 없음 vs 값이 0 | 평균이 오염된다 |

:::

넷 다 "타입이 같아서 통과하는" 오류입니다. 그리고 넷 다 **스키마에 의미를 적어두면 막히는** 오류입니다.

<!--figure: schema-layers | 이름과 타입은 대부분의 스키마가 적는다. 뚫리는 곳은 늘 그 아래층이다.-->

### 그래서 필드마다 네 가지를 적는다

::: {.formula}
[스키마 항목의 최소 구성]{.label}

- **이름** — 시스템 전체에서 단 하나의 표기. 축약형·별칭을 허용하지 않는다.
- **타입과 제약** — 형태, 길이, 허용값의 닫힌 집합.
- **의미 단위** — 유량인지 저량인지, 단독인지 누계인지, 어느 시점 기준인지, 단위가 무엇인지.
- **없을 때** — 결측을 무엇으로 표현하는지. 그리고 **지어내지 않는다**는 선언.
:::

세 번째와 네 번째가 대부분의 명세에서 비어 있습니다. 그리고 사고는 전부 거기서 납니다.

### 허용값을 닫으면 분기가 사라진다

의미를 적는 것만큼 강력한 것이 **닫힌 집합(closed set)** 입니다.

상태 필드를 `string`으로 두면 에이전트는 `"pending"`, `"PENDING"`, `"in_progress"`, `"processing"`을 상황에 따라 지어냅니다. 각각이 별개의 분기를 만들고, 어느 코드 경로에서는 대문자를, 어느 경로에서는 소문자를 비교합니다.

허용값을 `PENDING | DELIVERED | FAILED` 세 개로 못 박으면 그 자유도가 통째로 사라집니다. 그리고 **여기 없는 상태가 발생하면 그건 버그가 아니라 명세 누락**이라는 것이 분명해집니다 — 시스템이 조용히 세 번째 값을 첫 번째로 접는 대신, 어디를 고쳐야 하는지가 드러납니다.

### 스키마가 만든 불변식은 테스트로 내려온다

스키마의 마지막 힘은 **검증 가능한 불변식**을 준다는 것입니다.

"단독 4분기의 합은 연간과 같다." 이 문장은 스키마가 유량과 저량을 구분해 두었기 때문에 쓸 수 있습니다. 그리고 이 문장은 그대로 테스트가 됩니다. 사람이 눈으로 판정하지 않습니다. 합이 맞거나 틀리거나 둘 중 하나입니다.

::: {.callout}
좋은 스키마는 에이전트의 출력을 검사하는 문서가 아니라, **에이전트가 틀릴 수 있는 경우의 수를 미리 지워버리는 문서**입니다. 지워지지 않은 자유도만큼만 환각이 남습니다.
:::

:::::: {.fieldnote}
[현장 노트 — 스키마를 독립 문서로 두지 않아서 생긴 일]{.label}
[다트인사이트 저장소 · modules/pick_rule.py 정본화 이전]{.src}

정직하게 적자면, 저는 이 절이 말하는 것을 처음부터 하지 않았습니다.

다트인사이트에는 `03_DATA_SCHEMA.md` 같은 독립 문서가 없습니다. 스키마는 `ARCHITECTURE.md` 5절 「DB 스키마 — SQLite 22 테이블」 안에 들어 있습니다. 문서를 하나라도 줄이는 편이 관리가 쉬울 것 같았습니다.

그 대가를 나중에 치렀습니다. 청산 규칙 하나 — "고점 대비 −12%" — 가 **코드 세 군데에 각각 구현되어 있었고, 세 값이 서로 달랐습니다.** 어떤 계산은 종가를 기준으로, 어떤 계산은 장중 고가를 기준으로, 어떤 계산은 다른 기간 창을 썼습니다. 같은 규칙이라고 믿고 있던 세 코드가 서로 다른 답을 내고 있었습니다.

명세가 없어서가 아닙니다. **규칙이 산문 안에 있었기 때문입니다.** 아키텍처 문서의 문단 속에 적힌 임계값은 구현할 때마다 다시 해석됩니다. 결국 `modules/pick_rule.py` 하나를 정본으로 세우고 나머지를 그리로 끌어모아 봉합했습니다.

이 절이 스키마를 독립 문서로 올리라고 말하는 것은, 그렇게 해봐서가 아니라 **그렇게 하지 않아서 겪었기 때문**입니다.
::::::





## 04_UI_SPEC.md: 컴포넌트 계층 구조, 디자인 토큰, 사용자 인터랙션 규칙

프론트엔드 개발 현장에서 AI 에이전트가 만들어내는 가장 흔하고 절망적인 결과물은 [시각적 파편화(Visual Fragmentation)]{.dot}입니다.

"모던하고 깔끔한 대시보드 UI를 만들어줘"라는 지시를 내리면, AI는 첫 번째 페이지에는 `#3B82F6` 블루 톤의 Tailwind 버튼을 붙이고, 두 번째 모달 창에는 `#2563EB` 인디고 톤을 사용하며, 패딩(Padding)과 마진(Margin) 값은 컴포넌트마다 4px, 8px, 12px로 제각각 흩어집니다. 더 치명적인 것은 인터랙션의 붕괴입니다. 로딩 스피너가 버튼 바깥에서 돌거나, ESC 키를 눌렀을 때 모달이 닫히지 않고, 모바일 뷰포트에서 사이드바가 본문을 가려버리는 식의 파편화가 발생합니다.

이 혼란을 잠재우는 문서가 바로 4대 명세의 마지막 퍼즐인 `04_UI_SPEC.md`입니다. 이 문서는 디자이너의 피그마(Figma) 시안을 AI 에이전트가 오차 없이 코드로 옮길 수 있도록 규격화한 '프론트엔드 조립 설계도'입니다.

### 디자인 토큰(Design Tokens): 시각적 임의성 박멸

AI 에이전트가 CSS나 스타일 코드를 임의로 지어내지 못하게 하려면, 색상, 타이포그래피, 여백, 곡률(Radius)의 유효 범위를 엄격히 닫힌 집합으로 정의해야 합니다.

::: {.formula}
[디자인 토큰의 세 축]{.label}

- **Color Palette** — 임의의 Hex 코드가 아닌 시맨틱 네이밍(`primary`, `background`, `surface`, `border`, `text-muted`)으로 한정.
- **Spacing Scale** — 4px 그리드 기반(4, 8, 16, 24, 32, 48px) 외의 홀수 패딩 사용 금지.
- **Typography** — H1부터 본문(Body), 캡션(Caption)까지의 폰트 크기, 줄 간격(Line-height), 글자 두께(Weight) 매핑.
:::

디자인 토큰이 명세서에 상수로 박혀 있으면, 에이전트는 CSS 클래스를 작성할 때 `bg-blue-500`과 같은 임의의 유틸리티 클래스 대신 사전에 약속된 테마 토큰(`bg-background-surface`, `text-text-primary`)만을 일관되게 조립합니다.

### 컴포넌트 계층 구조(Component Hierarchy Tree)

프론트엔드 코드가 스파게티로 변하는 가장 큰 이유는 상태와 UI의 책임 분리가 무너지기 때문입니다. 에이전트는 흔히 500줄이 넘는 단일 파일 안에 헤더, 사이드바, 본문 뷰어, 모달 로직을 전부 때려 박습니다.

`04_UI_SPEC.md`는 페이지 전체의 트리 구조(DOM Hierarchy)와 컴포넌트별 단일 책임(Single Responsibility)을 사전에 선언해야 합니다.

```text
<AppLayout>
  ├── <SidebarContainer> [Stateful: 선택된 파일, 검색어]
  │     ├── <VaultHeader> (문서 개수, 설정 버튼)
  │     ├── <SearchInput> (디바운스 키워드 입력)
  │     └── <DocumentTreeList> (가상 스크롤 목록)
  │           └── <DocumentTreeItem> (활성 상태 표시)
  └── <MainViewerContainer> [Stateful: 파싱된 AST, 스크롤 위치]
        ├── <ViewerHeader> (문서 제목, 태그 뱃지, 액션 버튼)
        ├── <MarkdownRenderer> (수식, 코드 블록, 본문)
        └── <StatusBar> (단어 수, 마지막 동기화 시간)
```

이와 같이 부모-자식 간의 계층 구조와 어느 컴포넌트가 '상태(State)'를 소유하는지 명세에 적시해 두면, 에이전트는 자연스럽게 컴포넌트를 원자 단위로 쪼개어 파일별로 모듈화합니다.

### 사용자 인터랙션 및 키보드 단축키 규칙

파워 유저를 위한 생산성 도구일수록 마우스 클릭뿐만 아니라 키보드 내비게이션, 포커스 트래핑, 반응형 브레이크포인트에 대한 규칙이 정밀해야 합니다.

::: {.formula}
[인터랙션 선언 항목]{.label}

- **키보드 단축키** — `Cmd/Ctrl + K`(검색창 포커스), `Esc`(모달 및 검색창 닫기), `J` / `K`(문서 목록 상하 이동).
- **반응형 상태 전이(Breakpoints)** — 데스크톱(1024px 이상)은 2-Pane 레이아웃(사이드바 320px 고정, 메인 뷰어 가변), 모바일(768px 미만)은 1-Pane 레이아웃(햄버거 메뉴를 통한 드로어 슬라이드).
- **로딩 및 빈 상태(Empty States)** — 문서가 선택되지 않았을 때의 Placeholder 일러스트 및 안내 문구, 파싱 중일 때의 Skeleton UI 표시 규격.
:::

## 4대 명세 간 교차 검증(Cross-Referencing)을 통한 정합성 검증

<!-- ⚠ 문장은 초안이다. 저자의 목소리로 다시 쓸 것. -->

네 개의 문서를 다 썼다고 명세가 완성된 것이 아닙니다.

4대 명세는 서로 독립된 네 편의 글이 아닙니다. **같은 개념이 네 문서에 각각 다른 얼굴로 나타납니다.** PRD의 "문서"는 스키마에서 테이블이 되고, 아키텍처에서 데이터 흐름의 한 마디가 되고, UI 명세에서 화면에 뿌려지는 값이 됩니다. 같은 것을 네 번 적는 셈이고, **네 번 적으면 어긋납니다.**

### 검증해야 할 것은 문서가 아니라 쌍이다

문서가 넷이면 대조해야 할 쌍은 여섯입니다. 넷이 아닙니다.

<!--figure: cross-reference | 문서를 하나 늘릴 때마다 검증할 쌍은 제곱으로 는다. 4개에서 멈추는 이유다.-->

::: {.table-wrap}
| 쌍 | 무엇을 대조하는가 |
|---|---|
| **PRD ↔ SCHEMA** | 요구사항에 등장하는 모든 명사가 엔티티나 필드로 존재하는가. 반대로 아무 요구사항도 참조하지 않는 필드가 있는가 |
| **PRD ↔ ARCHITECTURE** | 각 기능이 어느 계층에서 처리되는지 정해졌는가. [Phase] 태그가 두 문서에서 일치하는가 |
| **PRD ↔ UI_SPEC** | 안티 골(Non-Goals)로 배제한 기능의 화면이 남아 있지 않은가 |
| **SCHEMA ↔ ARCHITECTURE** | 스키마의 모든 테이블이 데이터 흐름 어딘가에 등장하는가. 상태 필드의 허용값이 상태 머신의 상태 집합과 같은가 |
| **SCHEMA ↔ UI_SPEC** | 화면이 표시하는 모든 값이 스키마에 있는가. **역도 성립한다** — 스키마에만 있고 어느 화면도 쓰지 않는 필드는 죽은 필드다 |
| **ARCHITECTURE ↔ UI_SPEC** | 상태 전이가 화면의 로딩·에러·빈 상태와 대응하는가 |
:::

문서를 다섯 개로 늘리면 쌍은 열 개가 됩니다. 여섯 개로 늘리면 열다섯입니다. **명세 문서를 넷에서 멈추는 이유가 여기 있습니다** — 층위를 더 쪼개는 이득보다 대조 비용이 먼저 터집니다.

### 언제 하는가 — 코드가 나오기 전에

교차 검증은 **Phase를 시작하기 직전**에 합니다. 코드가 한 줄이라도 나온 뒤에 하면, 발견된 모순은 이미 구현으로 굳어 있습니다.

그리고 이것은 사람이 눈으로 하는 일이 아닙니다. 여섯 쌍을 사람이 대조하면 반드시 놓칩니다. 에이전트에게 시킵니다.

```bash
claude "Read all four specs in docs/specs/.
Cross-reference them and report ONLY inconsistencies. For each finding give:
  (1) the two documents that disagree
  (2) the exact conflicting lines
  (3) which one is more likely correct, and why
Do NOT fix anything. Do NOT generate code. Report gaps, not style preferences."
```

마지막 두 줄이 중요합니다. 고치라고 하면 에이전트는 **한쪽을 다른 쪽에 맞춰 조용히 덮습니다.** 어느 쪽이 진실인지는 사람이 정해야 합니다.

### 실제로 해보면 — 이 책의 명세도 어긋나 있었다

이 절을 쓰면서 우리 실습 프로젝트의 4대 명세에 위 프롬프트를 그대로 돌렸습니다. 다섯 건이 나왔습니다.

::: {.table-wrap}
| 항목 | 한쪽 | 다른 쪽 | 판정 |
|---|---|---|---|
| `user_id` 외래 키 | 제3장 스키마 템플릿에 선언 | 제5장 실전 DDL에 없음. `users` 테이블 자체가 없음 | 모순 |
| `is_public` | 제3장 [Phase 3]에 선언 | 제5장 DDL에 없음 — 그런데 **공유 뷰어 코드가 이 필드를 참조** | 모순 |
| `share_slug` · `api_access_count` | 제3장에 선언 | 제5장 DDL에 없음 | 모순 |
| `tsv_content` 생성 방식 | 제4장 아키텍처는 "토큰화 **트리거** 실행" | 제5장 DDL은 `GENERATED ALWAYS AS … STORED` | 모순 |
| `title` 길이 | API 계약은 "1자 이상 **100자** 이하" | DDL은 `VARCHAR(255)` | 모순 |
:::

다섯 건 모두 **타입 오류가 아닙니다.** 각 문서만 따로 읽으면 완벽하게 정합적입니다. 컴파일러도 스키마 검증기도 잡지 못합니다. 오직 문서와 문서를 맞대야 드러납니다.

그리고 두 번째 줄이 이 절의 존재 이유를 그대로 보여줍니다. **명세에 없는 필드를 코드가 이미 쓰고 있었습니다.** 스키마를 진실로 삼겠다고 선언한 프로젝트에서, 코드가 스키마보다 앞서 나가 있었던 것입니다.

:::::: {.worksheet}
#### 교차 검증 체크리스트 — Phase 시작 전 1회

1. PRD의 명사를 전부 뽑아 스키마 엔티티·필드와 대조한다. **양방향으로** 한다.
2. 스키마의 상태 필드 허용값과 아키텍처의 상태 머신 상태 집합이 **같은 집합인지** 확인한다.
3. UI가 표시하는 값을 전부 뽑아 스키마에 있는지 본다. 없으면 UI가 앞서간 것이다.
4. 스키마에 있는데 어느 화면도, 어느 API도 쓰지 않는 필드를 찾는다. 죽은 필드는 지운다.
5. 안티 골(Non-Goals)로 배제한 기능의 흔적이 다른 문서에 남아 있는지 본다.
6. 같은 값의 제약(길이·범위·형식)이 문서마다 다른지 대조한다.
7. 발견된 모순마다 **어느 쪽이 진실인지 사람이 결정하고**, 진 쪽을 고친다.
::::::

7번이 핵심입니다. 모순을 발견하는 것보다 어려운 일이 **어느 쪽을 살릴지 정하는 것**입니다. 대개는 코드가 진실입니다 — 실제로 돌아가고 있으니까요. 명세를 사후에 코드에 맞추는 것은 굴복이 아니라 정직입니다. 다만 그렇게 맞춘 뒤에는, 다음부터 명세가 앞서도록 순서를 되돌려야 합니다.

::: {.callout}
4대 명세를 다 쓰는 것은 절반입니다. 나머지 절반은 **네 문서가 같은 시스템을 말하고 있는지 확인하는 일**입니다. 이 검증을 건너뛰면, 각각은 완벽하고 전체는 틀린 명세가 만들어집니다. 그리고 에이전트는 그 틀린 전체를 아주 성실하게 구현합니다.
:::
